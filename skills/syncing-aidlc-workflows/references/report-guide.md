# HTML レポートの解説枠の書き方

`aidlc_report.sh` は上流差分を**サイドバイサイドの自己完結 HTML**に書き出す。目的は「利用者が
ブラウザでパッと変更内容を確認できる」こと。役割分担は明確に分けている。

- **スクリプト（決定論・忠実）**: サイドバイサイド diff 本体、追加/変更/削除の統計、上流コミットログ。
  ここは機械的に正確に再現され、AI は手を入れない（diff の忠実性が崩れると確認手段として無価値になるため）。
- **Claude（解釈）**: 「まとめ」「変更で何が起き挙動がどう変わるか」の2枠。差分の意味は自然言語の
  解釈であり決定論では出せないので、ここを Claude が埋める。

## 差し込み枠と編集方法

レポート HTML には次の2つの枠が**空のプレースホルダ**として出力される。

```html
<!-- AIDLC:SUMMARY:START -->
<p class="placeholder">（…）</p>
<!-- AIDLC:IMPACT:START -->
```

それぞれ `:START` と `:END` のコメントで挟まれている。Claude は HTML を `Read` し、**マーカーの間
（プレースホルダの `<p>`）を `Edit` で人間向け解説に置換**する。マーカー自体（`<!-- AIDLC:… -->`）は
残しておくと、再生成・再編集の目印になる。HTML 片を書くので、見出しは使わず `<p>` / `<ul><li>` /
`<code>` 程度の素朴なタグで十分（CSS はレポート側に同梱済み）。

## まとめ（SUMMARY 枠）

今回の上流更新を **2〜4 行**で要約する。読み手は「この更新を取り込むべきか」を判断したい。

- 何が新しくなったか（機能追加・修正・リファクタの別）。
- 利用者にとっての意味（使い方が変わる／設定が要る／単なる内部変更で影響なし、など）。
- 規模感（例: 「エージェント定義 3 件の更新と新規フック 1 件」）。

## 変更で何が起き、挙動がどう変わるか（IMPACT 枠）

**主要な変更ファイルごと**に、具体的な挙動・設定・ワークフローの変化を箇条書きにする。
diff の行を読み、「結果として何が起こるか」を翻訳する（diff をそのまま再掲しない）。観点:

- **新機能 / 追加**: 何ができるようになるか。導入に必要な操作があれば明記。
- **破壊的変更**: 既存の使い方・コマンド・設定キーが変わる箇所。移行に必要な手当。
- **自分のローカル変更への影響**: ローカルで編集していたファイルが上流でも変わった場合の注意
  （3-way マージで衝突しうる箇所）。
- **衝突（merge 後に生成した場合）**: `manifest.pendingUpdate.conflicts` に記録された各衝突の
  ファイル・種別（merge / delete-modified / add-add / binary 等）と、解消の方針。
- 影響が無い変更（typo 修正・整形のみ等）は「影響なし」とまとめてよい。

## 注意

- レポートは `.aidlc-sync/reports/` に生成される**再生成可能な成果物**で、git 管理対象外
  （import 時に `.aidlc-sync/.gitignore` で除外される）。チーム共有したい場合はファイルを別途配布する。
- 参考docs（`docs/`）の差分は件数のみヘッダに出る。docs は翻訳のみで install/マージ対象外なので、
  diff 本体には含めない（[architecture.md](architecture.md) の「参考docs」を参照）。
