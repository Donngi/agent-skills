# オニオンアーキテクチャのユースケース層を実装する

ユースケースは、UI 層から呼ばれ、ドメインモデルを使って1つの操作をやり遂げる。
やることは「取得する → ドメインモデルのメソッドを呼ぶ → 保存する → 結果を返す」の手順だけで、業務の判断はドメインモデルに任せる。

## 対象範囲

TypeScript を対象にする。ドメイン層は Zod で書かれた `type` と関数のモデル（公開 API のオブジェクト `Task.start` など、ブランド付きの型、`DomainError` 継承のエラー class）を前提にする。

書くのはユースケース層だけである。**ドメイン層（値オブジェクト・エンティティ・リポジトリやドメインサービスのインターフェース）は書かない。**
ユースケースに要るドメインの部品が足りないとき（リポジトリにメソッドが無い、業務の判定を置くメソッドが無いなど）は、
何がどこに要るかを回答に示し、ユースケースの中で代わりに実装しない。ドメインの部品は、プロジェクトのドメイン層の流儀で別に書く（`implementing-ddd-tactical-patterns-with-zod` スキルがあれば、それを使う）。
インフラ層の実装（リポジトリの実装など）と、ユースケースを組み立てる composition root も書かない。

## 進め方

1. **既存のドメインモデルを読む**（呼ぶエンティティの公開 API・ドメインのメソッドとその `@throws`・リポジトリとドメインサービスのインターフェース）
2. **手順を決める**（下の「手順の型」から当たるものを選ぶ）
3. **`references/usecase-code.md` と `references/errors.md` と `references/comments.md` を読んでから書く**。`example/usecase/` の該当する実物を読む
4. **テストを書く**（`references/testing.md` を読んでから書く）
5. **formatter と linter と型検査を通す**（プロジェクトの設定で。example の折り返し位置は真似しない）
6. **`references/checklist.md` を上から通す**

**プロジェクトに既存のユースケースがあれば、その流儀に合わせてよい。** 利用者の指示とプロジェクトの規則も、同じ範囲で既定を置き換えてよい。 下の規則は定めが無い場合の既定である。
**既存の流儀に合わせて既定を置き換えたときに外せる規則は、`references/checklist.md` の「既存の流儀で外せる規則」の表にあるものだけである。** 表に無い規則は、既存のコードが反していても合わせない。
書き直しを頼まれたユースケースそのものは、合わせる対象の「既存」に数えない。
外した規則と、置き換えの出どころのファイルを回答に書く。

## フォルダ構成

```
domain/                    ドメイン層（このスキルでは書かない）
usecase/
  shared-errors.ts         UseCaseError と、複数のユースケースに共通のエラー
  shared-errors.test.ts
  CreateTaskUseCase.ts     1ファイル1ユースケース
  CreateTaskUseCase.test.ts
```

テストは対象と同じ場所に `XxxUseCase.test.ts` で置く。

## 手順の型

| 型 | 手順 | 戻り値 | 実物 |
|---|---|---|---|
| 集約を作る | 前提の集約を取得 → 無ければ NotFound → 採番 → 生成する側の集約のメソッド（`Project.createTask`）→ 保存 | 作った集約の ID | `example/usecase/CreateTaskUseCase.ts` |
| 集約を作る（生成する側の集約が無い） | 採番 → 集約の `create`（生成の入口がほかに決まっていない集約のもの）→ 保存。前提の集約が無いなら取得しない | 作った集約の ID | example には無い。書き方は `references/usecase-code.md`「集約を作る」 |
| 集約を更新する | 取得 → 無ければ NotFound → 集約のメソッド（`Task.start`）→ 保存 | `void` | `example/usecase/StartTaskUseCase.ts` |
| 子エンティティを足す | 取得 → 無ければ NotFound → 集約ルートのメソッド（`Task.addComment`）に deps を渡す → 保存 | 足した子の ID | `example/usecase/AddTaskCommentUseCase.ts` |
| 参照する | 取得 → 無ければ NotFound → Result DTO にマッピング | Result DTO | `example/usecase/GetTaskUseCase.ts` |
| 一覧を参照する | リポジトリの一覧取得 → 返った順のまま Result DTO の配列にマッピング（0件でも NotFound にしない） | Result DTO の配列 | example には無い。書き方は `references/usecase-code.md`「参照する」 |

当たる型が無い手順（複数の集約を1つのユースケースで更新する、外部サービスを呼ぶなど）は、近い型の実物に倣い、
どこで失敗したら何が保存済みで残るかを回答に書く（`references/usecase-code.md` の「保存と失敗」）。

## 中核の規則

| # | 規則 | 理由 |
|---|---|---|
| 1 | ユースケースは `export type XxxUseCase = Readonly<{ run }>` と `export function createXxxUseCase(deps: XxxUseCaseDeps): XxxUseCase` で書く。1ファイル1ユースケース | 呼び出し側は型だけに依存し、テストでは deps を差し替えて組み立てられる |
| 2 | `run` の引数は `props: XxxUseCaseProps` の1つにする。プロパティはドメインが公開する型（ブランド付きの ID など）で受け取る。ドメインが `string` のまま持つ値（タイトルなど）は `string` で受け、件数のようにリポジトリのメソッドが `number` で受ける値は `number` で受ける | 外からの入力の検証は UI 層が `XxxId.create` などで済ませる。ユースケースが生の文字列を受けると、検証済みかどうかが型から分からなくなる |
| 3 | deps は `XxxUseCaseDeps` に、そのユースケースが使うものだけを書く。型はドメインのインターフェースで書き、インフラ層の実装を import しない | 依存の向きを内側だけに保つ。使わないものを deps に持たせると、テストで何を用意すればいいか読めなくなる |
| 4 | 業務の判断はドメインモデルのメソッドに任せる。ユースケースに業務の `if` を書かない（`filter` の述語や三項演算子で業務の条件を計算するのも同じ）。リポジトリが `undefined` を返したときの NotFound と、ドメインサービスが返した値を失敗にする分岐と、Result DTO へのマッピングで状態ごとに形を分ける `switch` と、ドメインの約束から到達しない分岐で `FatalUnreachableError` を投げる `if` は、業務の判定ではない（例。ほかに、握りつぶしたメソッドが成功したかで保存を分ける分岐、任意プロパティを置くかの分岐も業務の判定ではない） | ユースケースに判定を書くと、同じ規則を別のユースケースが通らずにすり抜ける。判定の置き場が無ければ、ドメインに要るメソッドを回答に示す |
| 5 | ドメインの値は `create` とドメインのメソッドだけで作る。`reconstruct` を呼ばない。スプレッドやリテラルでドメインの値を作らない。子エンティティの `create` を直接呼ばない | ブランドはスプレッドで引き継がれるので、不変条件を通らない値が型検査を通ってしまう |
| 6 | 保存の前に、ドメインのメソッドをすべて呼び終える。依頼が握りつぶすことを求めたメソッドが指定のエラーを投げたときも、すべてのメソッドを呼び終えてから保存する。握りつぶしたメソッドは新しい値を返さないので、その集約は直前の値のまま次の手順に進める。保存するのは、その集約で最後に成功したメソッドが返した値である。1つも成功しなかった集約は、取得した値のまま保存し直さない | 保存するのは、メソッドが返した新しい値だけにする。途中で失敗したときに、半端な状態を保存しない |
| 7 | 戻り値は、参照ならプリミティブだけの Result DTO（`XxxUseCaseResult`）、作成なら作った ID などの最小の値、子エンティティを足すなら足した子の ID（更新が主の手順で、子を足すのが付随なら、依頼が子の ID を求めたときだけ返す）、更新なら `void` にする。ドメインモデルを返さない | 呼び出し側がドメインモデルのメソッドや `reconstruct` に触れられないようにする |
| 8 | ドメインのメソッドや deps が投げるエラーを、呼び出し側（props を渡した側）が対処できる失敗かで分ける。対処できる失敗のうち、業務の異常系は異常系のパターンごとの `UseCaseError` 継承の class に、入力の形の不正は共有の `InvalidInputError` に詰め替え、元のエラーを `cause` に入れる。呼び出し側には直せない失敗（deps が契約に反する値を返したこと・保存先の壊れ・通信の失敗）は catch せずそのまま伝播させる。`run` の `@throws` には、ユースケースが投げるエラーだけを書く（`FatalUnreachableError` を除く。`references/errors.md`） | 呼び出し側は、ユースケースのエラーの class だけで分岐でき、ドメインのエラーの class を知らなくて済む。ドメインの詳細は `cause` から読める。直せない失敗まで詰め替えると、不具合が対処できる失敗に見えて隠れる |
| 9 | 時刻は deps の `clock` から、ID は deps の `idGenerator` か採番のドメインサービスから取る。`Date.now()` や `crypto.randomUUID()` を直接呼ばない | テストで値を固定できる |
| 10 | 依頼に無い手順・検証・ログ・リトライを足さない | 決まっていない仕様を勝手に固定することになる |

規則ごとの書き方と理由の詳細は references にある。

## 依頼に書かれていないことの扱い

- **手順に要るのに無いドメインの部品は、作らずに回答で示す。** ドメインに置くメソッドが無い判定を、ユースケースの `if` で代わりにしない。提案した部品は、次のどの場合もコードとして書かない
  - **依頼の中心の操作がドメインにあり、足りないのが並び順・原子性・絞り込みのような、操作の可否に関わらない部品だけなら**（権限や公開範囲で見せるものを絞る条件は、操作の可否の判定として扱う）、残りの手順を書いて型検査を通し、足りない部品が要る要件は満たせなかった要件として分けて書く。そのユースケースがしないこと（並べ替えない、片方だけ保存されうる）は、`run` の JSDoc にも書く（呼び出し側が満たされていると誤解しないようにする）
  - **足りないのが操作の可否を決める判定（「ユーザーが担当者のときだけ着手できる」のような権限や禁止の条件）なら**、ユースケースのコードを書かない。判定を省いて書くと、依頼が禁止した操作を通すコードになる。要る部品（ドメインサービスのインターフェースか、`Task.start` の引数）の入力・契約・`@throws` を回答で示す
  - **依頼の中心の操作そのものがドメインに無いなら**、ユースケースのコードを書かず、要るメソッドの入力・契約・`@throws` を回答で示す。取得だけして成功する実装や、何も変えずに保存する実装で代わりにしない
- **依頼が、`references/checklist.md` の「既存の流儀で外せる規則」の表に無い規則に反する形（手順を共有の関数にまとめる、想定外のエラーまで1つのエラーに詰め替えるなど）を求めたら、その形では書かない。** 規則どおりに書き、その要件は満たせなかった要件として理由と一緒に回答に書く。表にある規則なら、利用者の指示に合わせて置き換えてよい（外した規則を回答に書く）
- **どの操作のユースケースかも、呼ぶドメインの契約も特定できないなら、コードを書かず質問を返す。** 決まっていない業務の仕様をコードで固定しない
- **見つからないときの扱いが依頼に無いなら、NotFound のエラーを投げる。** リポジトリが `undefined` を返す約束なら、それを失敗にするのはユースケースの判断である
- **同時更新や複数の保存の原子性が依頼に無いなら、リポジトリの約束どおりにし、保証しないことを JSDoc に書き、何が保存済みで残りうるかを回答に書く。** トランザクションの仕組みを勝手に足さない

## コメントと用語

**スキルの規則をコードのコメントに書かない。** 「ユースケースは子エンティティの create を直接呼ばない」のような規則の言い直しは、
読む人の役に立たず、次にコードを書く LLM がそのまま写して広げる。コメントに書くのは、その行のコードについての、コードから読めないことだけである（`references/comments.md`）。

**読むのはエンジニアなので、英語のまま通じる技術用語を訳さない。** ID・clock・idGenerator・deps・Result DTO・プロパティ・マッピング・ラップ。
コードの名前（`Task.start`）を抽象的な言い換え（「業務操作」）で指さない。
**オニオンアーキテクチャの用語で書く。** 外側の層は「UI 層」「インフラ層」と呼び、ほかのアーキテクチャの用語（アダプタ・ポート・コントローラ・プレゼンター・インタラクター・ゲートウェイ）を混ぜない。

## 回答

- 依頼の要件をどこで満たしたかを書く。満たせなかった要件は、満たした要件と分けて、理由と残る制約を書く
- ドメインに足りない部品があったら、何をどこに足すかを書く
- どこで失敗したら何が保存済みで残るか（欠番、片方が保存済みで残るなど）を書く
- レビューを頼まれたら、規則違反・具体的な不具合・任意の改善提案を分けて書く。好みの違いを違反と断定しない
  - **このスキル（SKILL.md・references）に書いてある規則に反するものは、規則違反に入れる。** 手順の各行のコメント、訳しすぎた用語、使わないタグのように、読みやすさの話に見えるものも、規則に書いてあれば任意の改善提案にしない
  - 任意の改善提案に入れるのは、どの規則にも書いていない好みや提案だけにする
