# eval の設計と保守

`implementing-onion-usecases` の eval の設計の前提と、ファイルの構造。ケースの一覧は `CASES.md`、回し方は `RUNNING.md` にある。

## ディレクトリの中身

| パス | 中身 |
|---|---|
| `evals.src.json` | ケースと採点項目の正本。手で編集するのはこちら |
| `evals.json` | `build.py` が生成する skill-creator 形式のファイル。手で編集しない |
| `build.py` | `evals.src.json` から `evals.json` を生成し、整合を検査する |
| `CASES.md` | ケースの一覧と、何を測るか |
| `RUNNING.md` | skill-creator で回すときの決まり |
| `fixtures/` | 実行役に `files` で渡す既存コード（`fixtures/README.md`） |
| `expected-violations/` | レビューケースの期待違反とおとり。**実行役には渡さない** |
| `grading-aids/` | 6番の採点用の誤実装と参照テスト。**実行役には渡さない** |

# 設計の前提

## 何を測るのか

規則を守ってユースケースを書けるか。規則を暗唱できるかではない。測っていないものは `CASES.md` の「測っていないもの」にある。

## 4つのタスク種別

| 接頭辞 | 種別（`category`） | 何を測るか |
|---|---|---|
| `gen-` | 生成（`generation`） | 手順の型ごとに規則どおりに書けるか |
| `trap-` | 生成・誘惑（`trap`） | 依頼文が違反を誘うとき、規則を優先できるか |
| `review-` | レビュー（`review`） | 規則違反を見つけ、正しいものを誤って指摘しないか |
| `fix-` | 修正（`fix`） | 既存コードを壊さずに規則へ寄せられるか |

**生成・誘惑のケースには、独立した誘導を1つだけ入れる。** 2つ入れると、どちらで落ちたか読めなくなる。レビュー・修正は違反ごとに採点する。

## 題材を参照実装から外している理由

スキルは `example/` の実物を読ませる。題材が同じだと写すだけで満点が取れ、規則の適用ではなく検索を測ることになる。
そこで題材を図書館（貸出 `Loan`・蔵書 `Book`・利用者 `Member`）にし、参照実装の語彙（タスク・プロジェクト・コメント）を依頼文にも fixture にも使わない。
スキル本文（`SKILL.md`・`references/`）にも、図書館の語彙を書かない。書くと、評価の答えをスキルに渡すことになる。

## 基準ケースと識別ケース

- **基準ケース**（`discriminative: false`）。参照実装を写せば通ってよい。`SKILL.md` や `example/` を変えたときの回帰検出
- **識別ケース**（`discriminative: true`）。参照実装に無い条件に、規則を当てはめられるかを見る

基準ケースがスキルありで落ちたら、まず採点項目か依頼文の不備を疑う。識別ケースが落ちたら、規則の伝わり方を疑う。

## 合否の出し方

**スキルありの構成で、全採点項目の通過率が100%であることを合格とする。** 採点項目はすべて同じ重み。
スキルなしの通過率は、スキルの効き目を見る参考値である。

採点項目には次を守らせる。

- **1行に1つの条件**
- **合格条件は SKILL.md・references に書いてあることと、依頼が明示した要件だけにする。** 書いていないことを求めるなら、先に規則側に足す
- **条件に当たらないときの扱いを文言に書く**（「〜のときは満たしたものとする」）
- **規則で満たせない明示要件は、「満たせなかった要件として分けて書く／ドメインに要る部品を示す」を合格の経路にする。** 依頼文で実装手段（`Date.now` など）を名指ししない

## 採点項目の層

1. **規則 ID**（`[no-reconstruct]` など）。意味ベースの ID に1つの要求を持たせる
2. **プロファイル**。規則を対象ごとに束ねたもの。ケースは `inherits` で選ぶ
3. **ケース固有の観測**。「この題材で何を観測すれば判定できるか」を書く

ケース固有の行と同じ欠落を数える規則と、そのケースで空虚に真になる規則は、ケースの `excludes` で落とす。

# ファイルの構造

## evals.src.json

| キー | 中身 |
|---|---|
| `skill_name` | `implementing-onion-usecases` |
| `note` | このファイルの扱いのメモ |
| `profiles` | プロファイル名 → 採点項目の配列。各項目は `[規則ID]` で始める |
| `evals` | ケースの配列 |

### プロファイル

**配布先はこの表と各ケースの `inherits` だけが正である。** `build.py` が突き合わせる。

| プロファイル | 対象 | 配られているケース |
|---|---|---|
| `all` | コードを書く生成・誘惑・修正 | 1〜8・11〜21・25〜26 |
| `answer` | 回答の書き方 | 1〜5・7〜8・10〜21・25〜26 |
| `usecase` | ユースケースのコード | 1〜5・7〜8・11〜21・25〜26 |
| `query` | Result DTO を返す参照 | 3〜4・8・11・16・18・20〜21・26 |
| `test-core` | テストの存在・実行・検出力 | 1〜8・11〜21・25〜26 |
| `test-style` | テストの書き方 | 1〜8・11〜21・25〜26 |
| `review` | レビュー | 23〜24 |

### ケースのキー

| キー | 必須 | 中身 |
|---|---|---|
| `id` | ○ | 1からの連番。`CASES.md` の `#` と一致させる |
| `name` | ○ | 接頭辞付きの kebab-case |
| `category` | ○ | `generation` / `trap` / `review` / `fix` |
| `discriminative` | ○ | 識別ケースなら `true` |
| `inherits` | ○ | 配るプロファイル名の配列 |
| `excludes` | | 継承した採点項目から落とす規則 ID |
| `prompt` | ○ | 実行役に渡す依頼文 |
| `expected_output` | ○ | ケースの意図のメモ。**実行役には渡さない** |
| `files` | ○ | `evals/` からの相対パス。グロブを書いてよい。`build.py` が展開し、スキルのルートからの相対パス（`evals/fixtures/…`）に直して evals.json に出す |
| `assertions` | ○ | ケース固有の採点項目。レビューは `V1:`（期待違反）・`D1:`（おとり）で始める |

## build.py

```bash
python3 -B skills/implementing-onion-usecases/evals/build.py
# 渡すファイルだけで型検査が通るかも確かめる
python3 -B skills/implementing-onion-usecases/evals/build.py --typecheck --node-modules <example の依存を入れた node_modules>
# evals.json を書き換えずに同期だけを確かめる
python3 -B skills/implementing-onion-usecases/evals/build.py --check
```

止まる条件: 規則 ID の無い採点項目、同じ規則 ID の重複、継承側に無い `excludes`、`files` のファイル（グロブなら1件以上）が無い、
レビューケースの V / D の番号が `expected-violations/` の表の行と合わない、上のプロファイルの表が `inherits` と合わない、`--typecheck` で型検査が通らない。

## fixture のドメインの複製

`fixtures/library/domain/` が正本で、ほかの root（`library-*`）の `domain/` はその複製である。
複製側は直接編集しない。このスキルの開発リポジトリでは、リポジトリ直下の `scripts/sync-skill-examples.mjs` が一致を確かめる（`--fix` で正本から上書き）。
