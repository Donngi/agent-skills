# コメントと用語

JSDoc・`//` コメント・テストの説明・エラーメッセージに書くことと、使う用語。

## スキルの規則をコードに書かない

**このスキルの規則を、コードのコメントに書かない。** 次のような文は、その行のコードの説明ではなく規則の言い直しである。

```ts
// ✗ 規則の言い直し
// ユースケースは子エンティティの Comment.create を直接呼ばない
const commented = Task.addComment(task, params, deps);

// ✗ 規則の言い直し
// Result はドメインモデルを返さず、プリミティブだけの DTO にマッピングする

// ✗ 規則の言い直し
// 着手時刻は Task.start の引数で渡す。いつ着手したかを決めるのはユースケースである
```

読む人はコードを見れば何をしているか分かり、規則の理由はこのスキルにある。
コメントに書くと、次にユースケースを書く LLM がそれを写し、同じ文がすべてのファイルに広がる。

判断に迷ったら、**「この行を変えたら嘘になる文か」**を問う。どのユースケースの同じ場所に置いても同じように読める文なら、規則の言い直しなので書かない。

## コメントに書くこと

| 書く場所 | 何を書くか |
|---|---|
| `XxxUseCase` の型の JSDoc | 1行目に型名、2行目にそのユースケースが何をするか（`バックログのタスクに着手する。`） |
| `run` の JSDoc | 型と名前から分からない振る舞い（欠番が出る、既存の集約を更新して保存するときの同時更新の後勝ち、前提を確かめたあとの変化を防がない（`Project.createTask` の JSDoc にある）、依頼にあったがドメインに部品が無いのでこのユースケースは並べ替えをしない）と `@throws`（`references/errors.md`） |
| Props のプロパティの JSDoc | 何を渡すか。単位（`Unix epoch ミリ秒`）のように、型から分からない約束があればそれも書く。任意プロパティの無いときの形は、`exactOptionalPropertyTypes` が有効なら `?:` から読めるので書かなくてよい（書いてもよい） |
| Result・Deps のプロパティの JSDoc | 何の値かが名前だけで読めないとき（`/** 作ったタスクの ID */`）と、型から分からない約束があるとき（`Unix epoch ミリ秒`、clock の `now` が前回より小さい値を返さないこと）に書く。任意プロパティの無いときの形は、Props と同じく書かなくてよい（書いてもよい） |
| エラー class の JSDoc | 何が起きたか（`指定された ID のタスクが無かった。`） |
| 手順の中の `//` | その行のコードについての、コードから読めないこと。ドメインの約束に頼っている箇所（`追加したコメントは末尾にある（コメントは投稿順に並ぶ）`）、ライブラリの落とし穴 |

**タグは `@throws` と `@deprecated` だけを使う。** `@param`・`@returns`・`@example` は使わない。パラメータと戻り値は型と名前で読める。

**手順の各行に、何をしているかのコメントを付けない。** `// タスクを取得する` `// 保存する` はコードを読めば分かる。

## 文の書き方

- JSDoc は句点で閉じる（`/** 〜。 */`）。プロパティ名の言い換えで足りるなら名詞のままにし、句点を付けない（`/** 担当者 */`）
- `//` のコメントは、途中の文を句点で区切り、最後の文には句点を付けない
- 何が起きたかは能動で書く（「〜しようとした」）
- 日本語と英字の間には半角空白を入れる（`タスク ID`、`PR の URL`）

## 用語

**読むのはエンジニアなので、エンジニアがそう呼ぶ語で書く。英語のまま通じる技術用語を訳さない。**

| 書く | 書かない |
|---|---|
| ID | 識別子 |
| clock・`clock.now()` の値 | クロック・時計・クロックの時刻 |
| idGenerator | ID ジェネレーター |
| deps | 依存 |
| `TaskNumberIssuer` | 採番器 |
| プロパティ | 項目 |
| Result DTO | 結果 |
| マッピングする | 写す |
| ラップする・伝播させる | 包む・そのまま伝える |
| タイトル・PR・リクエスト | 表題・プルリクエスト・要求 |

**コードの名前（関数・型・メソッド）はそのまま書いて指す。** `Task.start`・`Project.createTask` を「業務操作」「生成する側の操作」のような抽象語で言い換えない。
検索で見つからず、どのメソッドの話か追えなくなる。

**テスト名と Given/When/Then では、モデル名を英名のまま書く。** `Task` を「タスク」と書くと、テストの中で呼び名が揺れる。
JSDoc・`//` コメント・エラーメッセージでは、業務の言葉として書いてよい（`バックログのタスクに着手する。`、`タスク ${taskId} が見つかりません`、`/** 着手するタスクの ID */`）。

日本語に定着した語はそのまま使う（採番・着手・タイムスタンプ・欠番）。訳さないことが目的ではなく、読む人が一番速く分かる語を選ぶことが目的である。

## アーキテクチャの用語

**オニオンアーキテクチャの用語で書く。**

| 書く | 書かない |
|---|---|
| UI 層（API のハンドラや画面） | アダプタ・プレゼンター・コントローラ |
| インフラ層（リポジトリの実装など） | アダプタ・ゲートウェイ |
| リポジトリやドメインサービスのインターフェース | ポート |
| ユースケース | インタラクター |

ヘキサゴナルアーキテクチャやクリーンアーキテクチャは、層の分け方と責務が別物である。用語を混ぜると、どの層の話をしているのかが読めなくなる。

**依頼がほかのアーキテクチャの語で来ても、コード・JSDoc・回答はオニオンの語で書く。** 「インタラクター」と頼まれても `XxxUseCase` を書く。依頼の語とこのスキルの語の対応を、回答で一度示すのはよい（「ご依頼のポートは `TaskRepository` のインターフェースに当たる」）。
