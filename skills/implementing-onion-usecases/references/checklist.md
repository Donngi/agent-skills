# 完了の確認

書き終えたら上から通す。**当たらない項目は飛ばし、適用外の項目を満たすためにコードを足さない。**
既存のプロジェクトの流儀で既定を置き換えた項目は、下の「既存の流儀で外せる規則」の表の範囲で、採用したほうに読み替える。

## 既存の流儀で外せる規則

**既存の流儀を採用して既定を置き換えたときに外せる規則は、次の表のものだけである。** 置き換えた範囲に当たる規則のうち、採用した流儀と食い違うものだけを外す。外した規則と、置き換えの出どころ（利用者の指示・プロジェクトの規則・既存のコード）を回答に書く。

| 置き換えた範囲 | 外せる規則 |
|---|---|
| ユースケースの形（メソッド名・組み立て方・class で書くなど） | 規則1（`Readonly<{ run }>` と `createXxxUseCase(deps)`、1ファイル1ユースケース）、`run` の引数を `props` 1つで受けること、ファイルのセクションの順（`references/usecase-code.md`） |
| 命名 | `references/usecase-code.md` の命名の表 |
| 置き場（フォルダ構成） | `SKILL.md` のフォルダ構成、テストの置き場 |
| エラーの返し方（`Result` を返す） | ドメインのエラーを `Result` の失敗にどう入れるか・どのエラーまで入れるか（規則8の詰め替え。同じ class のまま入れるのは詰め替えではない）、`@throws` の書き方（失敗で返す範囲を JSDoc に書く）、テストで失敗を確かめる書き方（`rejects`・`toThrow`） |
| ユースケースのエラーの基底 class と置き場 | `UseCaseError` を作ること（既存の基底 class を使う）、エラーの置き場（`references/errors.md`「置き場」）、エラー class のテストで `UseCaseError` のインスタンスを確かめること |
| テストの書式 | `references/testing.md` の書式の規則（`test` か `it`、テスト名の接頭辞、Given/When/Then のコメント、`describe` の立て方、モックの名前と作る場所、assertion の選び方） |

**表に無い規則は外せない。** 特に次は、既存のコードが反していても合わせない: 依存の向き（インフラ層の実装を import しない）・業務の判定をドメインに任せること・ドメインの値の作り方・保存の順・ドメインモデルを返さないこと・ユースケースのエラーが `DomainError` を継承しないこと・例外で投げる流儀なら、呼び出し側が対処できる失敗（業務の異常系と入力の形の不正）をユースケースのエラーに詰め替えること・想定外のエラーを別の class に詰め替えないこと・詰め替えるときは元のエラーを `cause` に残すこと・時刻と ID を deps から取ること・手順をユースケース間で共有する関数にせず、ほかのユースケースも呼ばないこと。

## 形

- [ ] `export type XxxUseCase = Readonly<{ run }>` と `export function createXxxUseCase(deps: XxxUseCaseDeps): XxxUseCase` で書いている
- [ ] 1ファイル1ユースケースで、ファイル名が `XxxUseCase.ts` になっている
- [ ] `run` の引数が `props: XxxUseCaseProps` の1つで、プロパティがドメインの型になっている
- [ ] deps がそのユースケースで使うものだけで、型がドメインのインターフェースになっている。インフラ層の実装を import していない
- [ ] clock が `now: () => Timestamp` になっている（時刻を使うときだけ）
- [ ] 型がすべて `Readonly<{ ... }>` になっている

## 手順

- [ ] 業務の判定の `if` を書いていない。判定はドメインのメソッドが行っている
- [ ] 取得・NotFound の判定・保存の手順を、ユースケース間で共有する関数にしていない
- [ ] 生成の入口がドメインで決まっているなら、それを通している（`Project.createTask`）
- [ ] 子エンティティを集約ルートのメソッドで足している。子の `create` を直接呼んでいない
- [ ] `reconstruct` を呼んでいない。スプレッドやリテラルでドメインの値を作っていない
- [ ] 保存の前にドメインのメソッドをすべて呼び終え、保存するのは集約ごとに最後に成功したメソッドの戻り値だけにしている（握りつぶしたときの扱いは `references/usecase-code.md`「保存と失敗」）
- [ ] 時刻を deps の clock から、ID を deps の idGenerator か採番のドメインサービスから取っている。`Date.now()`・`new Date()`・`crypto.randomUUID()` を呼んでいない
- [ ] 任意プロパティを、値があるときだけ置いている
- [ ] 依頼に無い手順・検証・ログ・リトライを足していない

## 戻り値

- [ ] ドメインモデルを返していない
- [ ] 参照なら Result DTO がプリミティブだけで書かれ、状態で分かれるなら union になっている
- [ ] 作成なら作った ID などの最小の値、子エンティティを足すなら足した子の ID（更新が主で依頼が求めないなら `void`）、更新なら `void` を返している

## エラー

- [ ] ユースケースが投げるエラーが `UseCaseError` を継承している（`FatalUnreachableError` は、ドメインのものも `usecase/shared-errors.ts` に置いたものも除く）
- [ ] 1つのユースケースだけが投げるエラーをそのファイルの末尾に置き（`InvalidInputError` は `usecase/shared-errors.ts`）、複数のユースケースが同じ契約で投げるエラーを `usecase/shared-errors.ts` に置いている
- [ ] ユースケースのファイル同士でエラーを import していない。同名の class を複数のファイルに定義していない
- [ ] 呼び出し側が対処できる失敗だけを、class を限定して詰め替え、元のエラーを `cause` に入れている（業務の異常系はパターンごとの class、入力の形の不正は `InvalidInputError`）
- [ ] 呼び出し側には直せない失敗（deps が契約に反する値を返したこと・保存先の壊れ・通信の失敗）を catch していない。ドメインのエラーを握りつぶしていない（依頼がベストエフォートを求めたときを除く）
- [ ] `try` が、詰め替えるエラーを投げる呼び出し1つだけを囲んでいる（その引数を作る式は含めてよい）
- [ ] 握りつぶすときは、指定された class だけを catch し、それ以外を再 throw している。握りつぶすことを JSDoc と回答に書いた。依頼が求めていないのに戻り値の形を変えていない
- [ ] `run` の `@throws` に、自分が投げるエラー（詰め替えたものは `cause` の class も）だけを並べている。詰め替えたドメインのエラー、想定外のエラー、`FatalUnreachableError`、握りつぶして外へ伝播する経路が残らない class を書いていない

## コメントと用語

- [ ] スキルの規則を言い直したコメントが無い
- [ ] `run` の JSDoc に、欠番や同時更新の後勝ち、依頼にあったがドメインに部品が無いのでこのユースケースはしないこと（並べ替え・まとめての保存）のような、型から分からない振る舞いを書いている
- [ ] 技術用語を訳しすぎていない（ID・clock・deps・プロパティ・マッピング）。コードの名前を抽象語で言い換えていない
- [ ] オニオンアーキテクチャ以外の用語（アダプタ・ポート・プレゼンター・コントローラ・インタラクター・ゲートウェイ）を使っていない

## テスト

- [ ] 保存するもの・戻り値・見つからない・想定する異常系ごとの詰め替えと `cause`・想定外のエラーの伝播を、それぞれ確かめている
- [ ] 握りつぶさないエラーで保存の前にユースケースが終わるとき（NotFound・ドメインのメソッドのエラー）に、保存のメソッドを呼ばないことを確かめている
- [ ] 保存したドメインの値の期待値をヘルパーで作り、テスト対象と同じドメインのメソッドで作っていない（戻り値の Result DTO や作った ID の期待値はリテラルでよい）
- [ ] Result DTO のマッピングを状態ごとに確かめ、任意プロパティが無いときにキーが無いことを確かめている
- [ ] 子エンティティを足すなら、子を1件以上持つ集約に足して、足した子の ID が返ることを確かめている
- [ ] 一覧を返すなら、リポジトリが返した順のまま返ることと、空のとき空の配列を返すことを確かめている
- [ ] ユースケースのエラー class のテストがある
- [ ] 保存するものや戻り値を比べる正常系で、そこに流れる props の値をヘルパーの既定値やほかのプロパティの値と違うものにしている
- [ ] 結果を変える引数（ID・件数）をリポジトリやドメインサービスに渡しているなら、`toHaveBeenCalledWith` で確かめている
- [ ] リポジトリごとに保存が1回なら、正常系のいずれか1つで `toHaveBeenCalledTimes(1)` を確かめている
- [ ] Given / When / Then が全テストにあり、テスト名が `正常系: ` `異常系: ` で始まる

## 回答

- [ ] 依頼の要件をどこで満たしたかを書いた。満たせなかった要件を、満たした要件と分けて書いた
- [ ] ドメインに足りない部品があれば、何をどこに足すかを書いた。中心の操作があり、足りないのが操作の可否に関わらない部品（並び順・原子性・絞り込み。権限や公開範囲の絞り込みは除く）だけなら残りの手順を書いた
- [ ] 足りないのが操作の可否を決める判定（権限や禁止の条件）か、中心の操作そのものなら、ユースケースのコードを書いていない
- [ ] どこで失敗したら何が保存済みで残るかを書いた
