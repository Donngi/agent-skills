# 対話モデリングガイド — ユーザーとの対話でドメインモデルを作る

実装前のモデリングセッション。質問は**オープンクエスチョン禁止・意味のある選択肢2〜5個 + その他**の形式で行い、各段階の合意を JSON に反映しながら進める。一度に全部聞かず、段階ごとに小さく確認する。

## 進め方（5段階）

### 1. ドメイン概要

まずユーザーに自由に語ってもらう（ここだけは自由記述でよい）。聞き取るもの:
- 何のシステムか、中心となる業務は何か
- 境界づけられたコンテキストの名前になりそうな言葉（注文、請求、在庫…）

複数の業務領域が出てきたら「今回モデリングする範囲はどれか」を選択肢で確認する（1ファイル = 1コンテキスト）。

### 2. 中心概念の抽出

ユーザーの語りから名詞を拾い、候補一覧を提示して確認する。

> この領域の中心概念はこのあたりでしょうか？
> (1) 注文・注文明細・顧客・商品 でモデリングを始める
> (2) 追加したい概念がある
> (3) 削りたい概念がある

このとき**ユビキタス言語**を確定する（英語名も一緒に決める。コードのクラス名になる名前）。

### 3. 集約境界の決定（最重要）

判断基準はこれ一つ: **「一緒に変更され、1トランザクションで整合性を保つべき単位はどれか」**。

- 「注文を確定するとき、同時に必ず正しくなければならないものは？」→ 注文明細・合計金額 → 同一集約
- 「注文を確定するとき、顧客情報も同時に更新される？」→ No → 顧客は別集約、ID 参照

集約候補ごとに選択肢で確認:
> OrderLine は Order 集約の中に含めますか？
> (1) 含める — 明細は注文と常に一緒に変更される（推奨）
> (2) 独立した集約にする — 明細を単独で更新するユースケースがある
> (3) その他

決まったら各集約の `rootEntity` と、集約間の `relations`（ID 参照）を JSON に反映する。

### 4. VO・enum・不変条件

集約ごとに掘り下げる:
- 「金額・数量・ID のような**値そのもの**に意味がある概念は？」→ VO 候補（Money, Quantity, OrderId…）
- 複数集約で使う汎用語彙（Money 等）→ `sharedValueObjects` へ
- 「状態は何種類？」→ enum 候補（OrderStatus…）
- **不変条件を必ず聞く**: 「Order が絶対に守るべきルールは？（例: 合計金額は明細の合計と一致）」→ `invariants` へ。ここが図の価値の中心

### 5. 仕上げ

- 集約を跨ぐ計算・判断があれば Domain Service を提案（「この計算はどの集約にも置きにくいので OrderPricingService にしませんか？」）
- 業務上意味のある出来事があれば Domain Event を提案（「注文確定は他の文脈にも影響しますか？ OrderPlaced イベントにできます」）
- validate → render → HTML をユーザーに見せて、集約境界・参照方向をレビュー

## 対話中の注意

- ユーザーの語彙をそのまま使う（勝手に技術用語へ言い換えない）。ただし UseCase / DTO / 画面 という言葉が出てきたら「それはドメインモデル図の外側です」と説明し、図には載せない
- ユーザーが「画面も図に載せて」と求めたら: このスキルの目的（ドメイン層に閉じたピュアな図）と検証で機械的に拒否されることを説明し、別の図（画面遷移図等）を別途作ることを代替案として提示する
- 1段階進むごとに JSON を更新して validate を回す。最後にまとめて書くと手戻りが大きい
