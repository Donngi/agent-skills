# 完了の確認: コメントとメッセージ

`references/checklist.md` の項目と合わせて確かめる。確認するのは、対象に該当し、今回採用した規約で有効な項目だけである（適用の考え方は `SKILL.md` の「完了の確認」）。

- [ ] JSDoc に書いた制約が、スキーマで実際に検証されている
- [ ] スキーマのエラーメッセージが、その検査が実際に見ていることを書いている（`min(1)` を「必須」と書いていない）
- [ ] 利用者が読むメッセージ（スキーマのメッセージと `DomainError` のメッセージ）が「です」「できません」で言い切ってあり、依頼の形（「〜で指定してください」）や、どちらでもない語尾（「〜は置けません」「〜が重複しています」）になっていない
- [ ] 同じ規則を検査する箇所が複数あるとき、メッセージの文言が一致している
- [ ] JSDoc に制約を書き写していない（コードで読める min / max / regex / enum を繰り返していない。並び順・単位・境界で同じ値を許すかのように、利用者が頼る約束は書いてよい）
- [ ] プロパティと型の JSDoc に、設計の都合に由来する理由（「別の集約なので識別子で参照する」など）を書いていない（業務の知識に由来する理由は書いてよい）
- [ ] 〔check.mjs〕JSDoc のタグが `@throws`（と廃止予定の `@deprecated`）だけで、`@param` `@returns` `@remarks` `@example` を使っていない
- [ ] 関数名の言い換えを JSDoc に書いていない
- [ ] 説明を書いた JSDoc が文として読める日本語になっている（名詞1語の項目説明には句点を付けていない）
- [ ] 〔check.mjs〕`//` のコメントの最後の行に句点が付いていない（途中の文は句点で区切っている）
- [ ] エラーの説明が能動で書かれ、「範囲」「上限」が何の範囲・何の上限か分かる
- [ ] JSDoc に書いた順序・件数の約束を、実装が保証できている
- [ ] 例外を投げるすべての関数に `@throws` があり、呼び出し側が受け取りうるエラー種別（その関数自身が投げるものと、中で呼んだ具体的な関数から伝わるもの）が `FatalUnreachableError` を除いて漏れなく並んでいる（`createXxx` / `reconstructXxx` / `fromXxx` も書く。注入した依存が投げるものは、そのインターフェースの `@throws` に任せている）
- [ ] インターフェースのメソッドに、実装が投げるドメインエラーが `@throws` で書かれている
- [ ] インターフェースの実装のメソッドにも、自分で投げるものと、中で呼んだ具体的な関数（DTO の `fromXxx` など）から伝わるものが `@throws` で書かれている
- [ ] 公開する操作と依存の型の JSDoc に、型で表せない比較範囲・単位・採番の保証が残っている
- [ ] 規約に従ったことを報告するだけのコメントが入っておらず、コメントが置いた場所の実装と食い違っていない
