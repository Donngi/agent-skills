# 完了の確認: インフラ

`references/checklist.md` の項目と合わせて確かめる。確認するのは、対象に該当し、今回採用した規約で有効な項目だけである（適用の考え方は `SKILL.md` の「完了の確認」）。

- [ ] 1件取得のインターフェースが「無かった」ときに `undefined` を返している（エラーを投げていない）
- [ ] DTO の `to` が、保存形式にする前に完成値スキーマで値を確かめ、失敗を `FatalUnreachableError` に包んでいる
- [ ] DTO の名前が保存先の語彙 + モデル名 + `DTO` で終わっており、スキーマ・型・変換関数・ファイル名のすべてで揃っている
- [ ] DTO スキーマに値の制約（`min` / `max` / `regex` / `uuid` / `int` / `nonnegative`）が無い（保存キーの形式を除く）
- [ ] 保存キーが本体から導出できるなら、その整合を条件ごとに `superRefine` の issue で検証している
- [ ] DTO → ドメインの変換が `safeParse` で、失敗を `InvalidReconstructParamError` に包んでいる
- [ ] ドメイン → DTO の変換も `safeParse` で、生の `ZodError` が層の外に出ていない
- [ ] DTO の判別子が `literal`、列挙が `enum` で、DTO の変換を終えたあとの値が `XxxSchemaInput` に代入できる（保存キーを除くだけの設計なら、除いた値がそのまま代入できる）
- [ ] DTO のオブジェクトが入れ子まで `strictObject` で、保存キーと本体の整合を `superRefine` で検証している
- [ ] ドメインから DTO に import している定数が無い（保存形式だけが使う定数はインフラ層が自分で持っている）
- [ ] 保存キーの組み立てが DTO のファイルに1箇所だけあり、リポジトリ実装がそれを呼んでいる（キー文字列を手で書いていない）
- [ ] `Query` が使うパーティションキーも DTO の生成関数を共有している
- [ ] `superRefine` から呼ぶ分解関数が、形式違反の文字列でも例外を投げない
- [ ] ドメインが受理する境界値を DTO の `to` が通す（保存形式が有効なドメイン値をすべて表現できる）
- [ ] 保存先に1件あたりの容量の上限があるなら、件数と文字数が上限いっぱいの値でも収まることを DTO のテストで確かめている
- [ ] 集約の同時更新の扱いを要件として決めている（定めが無ければ楽観ロックを提案して確認している。検出を省くなら、インターフェースの JSDoc にそう書いている）
- [ ] 固定桁の保存キーを使うなら、ドメインが受け入れる番号と採番が返す番号をすべて表現できる
- [ ] 外部応答の型を、文字列化や数値化で失う前に検証している
- [ ] インフラ層が公開 API のオブジェクトを作らず、必要なものを名前付きで export している
