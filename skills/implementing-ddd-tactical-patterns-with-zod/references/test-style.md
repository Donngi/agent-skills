# テストの書き方

テストコードをどう書くかの規則。**何を確かめるか**は `references/testing.md` と、その冒頭の表で選ぶ `references/testing-*.md` にある。
実物は `example/` にある。テスト（`*.test.ts`）は全モデルぶん、ダミー生成ヘルパー（`*.helper.test.ts`）は値オブジェクトとエンティティのぶん揃っている。
揃っているのはモデルであって観点ではない。任意項目は `Task` の `pullRequestUrl` が実物。参照実装のモデルに無い契約（導出値など）の実物は無い。

**この文書は、どのテストを書くときも全体を読む。** 書くテストに応じて、次のファイルも全体を読む。
読むファイルは `SKILL.md` の「読む計画」の表が正で、次の表はその写しである。

| 書くもの | 読むもの |
|---|---|
| どのテストでも | この文書 |
| 値オブジェクト・エンティティのテスト | `references/test-style-helpers.md`（ダミー生成ヘルパー） |
| エラー class のテスト | `references/test-style-errors-tests.md` |
| リポジトリ実装、保存先に問い合わせるドメインサービスの実装 | `references/test-style-mocks.md`（クライアントのモック） |
| 型のテスト（`Xxx.test-d.ts`） | `references/test-style-type-tests.md`。何を置くかは `references/testing.md` |
| 書き終えたあとの網羅の確認 | `references/test-style-coverage.md`（カバレッジ） |
| Vitest 以外のライブラリ、テストを実装ファイルの中に書くか迷ったとき | `references/test-style-other.md` |

---

## どの書き方に従うか

候補は次の4つで、上ほど優先する。

1. 利用者が今回の依頼で明示した指示
2. 文書化されたプロジェクトの規則（`CLAUDE.md`、`docs/` のテストの記述）
3. 対象の周辺で一貫している既存の流儀（テスト設定ファイル、既存のテストファイル）
4. この文書の既定

**1 は確認せずに従う。** 利用者がすでに決めたことを聞き直さない。

**2 と 3 は、この文書の既定とぶつかる項目だけを、テストを書く前に利用者に確認する。**
見つけた規則や流儀の出どころ（ファイルのパス）と、それがどの項目（ライブラリ、置き場、命名、
Given / When / Then、テーブル駆動、ヘルパー）でどうぶつかるかを示して、どちらに従うかを聞く。
ぶつからない項目は確認しない。既存がこの文書の既定と同じなら、そのまま書けばよい。

**確認できない場面では、既存に従って進める。** サブエージェント・CI・評価のような非対話の実行では、
2、3 の順に従い、既定と違う書き方にした項目と、その出どころを回答に書く。確認待ちで止まらない。

**回答には、既定と食い違う項目を1つずつ、次の3つを揃えて挙げる。** 「既存に合わせた」とまとめて書くだけでは、
どの項目が既定と違い、何を根拠に既定を外したのかが読み手に分からない。新しいファイルのパスに現れるだけの違い（置き場やファイル名）も、項目として挙げる。

- 項目と、この文書の既定（「置き場: 既定は対象の横の `Xxx.test.ts`」）
- 採った書き方（「`src/__tests__/` に `Xxx.spec.ts`」）
- 出どころのファイルのパス。流儀なら、一貫していると判断したファイルをすべて挙げる（「`src/__tests__/Order.spec.ts`・`src/__tests__/Customer.spec.ts`」）。「既存の2ファイル」のように数だけで書かない

既定と同じだった項目は挙げなくてよい。

1〜3 のどれにも当たらなければ、確認せずにこの文書の既定で書く。ライブラリは Vitest を使う。

既存のテストが1つ見つかっただけで、その全部の特徴をプロジェクトの規則とみなさない。
項目ごとに、どこに書いてあるか、何ファイルで一貫しているかを示す。

**観点（`testing.md`）は書き方と別に扱い、既存のテストに無いことを省く理由にしない。**
プロジェクトが例外ではなく `Result` を返すなど、観点をそのまま当てはめられないときは、
どう読み替えるかも同じ確認に含める。

この確認はテストだけに掛かる。モデルのコードのフォルダ構成・区切り・エラー方式は、
`SKILL.md` のとおり既存に合わせる。

## 範囲

**このスキルが扱うのは、本物の外部接続を使わずに手元で完結するテストである。**

| 扱う | 扱わない |
|---|---|
| 値オブジェクト、エンティティ、エラー class | 本物のクライアントで実際の保存先に接続するテスト |
| DTO の `to` / `from`、保存キーの生成 | 実際の保存先でしか確かめられない契約（条件式の評価、並び順、原子性、競合） |
| クライアントをモックに差し替えた、リポジトリ実装とドメインサービス実装 | |

リポジトリ実装とドメインサービス実装は、クライアントをモックに差し替えて、送るコマンドと、
応答からドメインの値を組み立てる処理を確かめる（`references/test-style-mocks.md`）。
本物のクライアントを使うテストは、統合テストの仕組みで別に書く。

## 置き場と命名

| ファイル | 置き場 | 中身 |
|---|---|---|
| `Xxx.test.ts` | 対象 `Xxx.ts` の横 | テスト |
| `Xxx.helper.test.ts` | 対象 `Xxx.ts` の横 | ダミー生成ヘルパー。テストは書かない |
| `Xxx.test-d.ts` | 対象 `Xxx.ts` の横 | 型のテスト。Vitest の型検査モードで確かめる（`references/test-style-type-tests.md`） |

**`Xxx.helper.test.ts` はテストを登録しないので、テストの収集対象から外す設定を必ず入れる。**
Vitest の既定の収集対象は `**/*.{test,spec}.?(c|m)[jt]s?(x)` で、`Xxx.helper.test.ts` もこれに当たる。
外さないと `No test suite found in file` でテストの実行全体が失敗する（実測）。

```ts
// vitest.config.ts
import { configDefaults, defineConfig } from "vitest/config";

export default defineConfig({
	test: {
		// ヘルパーはテストを登録しないので、収集すると No test suite found で落ちる
		exclude: [...configDefaults.exclude, "**/*.helper.test.ts"],
	},
});
```

`exclude` を上書きするときは `configDefaults.exclude` を残す。消すと `node_modules` の中まで収集する。
`passWithNoTests` で失敗を消さない。テストを書き忘れたファイルまで通るようになる。
**Vitest の設定がまだ無いプロジェクトでは、この設定と型検査（`references/test-style-type-tests.md`）を入れた `vitest.config.ts` を確認せずに新しく作り、作ったことを回答に書く。**
既存の設定に足すときは、変える内容を示して利用者に確認する（`SKILL.md` の「書いたコードを check.mjs で確かめる」）。
ヘルパーの名前を `*.helper.ts` などに変えて、この設定を避けない。

ヘルパーは本番コードから import しない。

**`describe` は対象の操作単位で1つずつ作る。** ドメイン層は公開 API のキー単位で
`describe("Task.create")`、`describe("Task.start")`、`describe("TaskSchema")`。
**インフラ層は公開 API のオブジェクトを作らないので、export した関数名で立てる**
（`describe("fromDynamoDBTaskItemDTO")`、`describe("toDynamoDBTaskItemDTOPKSK")`）。
ファイル全体を包む `describe("Task")` は作らない。ファイル名で分かる。
**export した定数（`TASK_NUMBER_MAX` のような上限）には `describe` を立てない。** 定数は呼ぶ操作ではなく、
その境界はそれを使う検証の一部である。境界のテストは、その定数を使う操作の `describe`（`describe("TaskId.create")`・`describe("TaskIdSchema")`）の中に書く。
型のテストは `Xxx.test-d.ts` に、`describe("Task.create の型")` のように立てる。
**エラー class は、どのファイルにあっても class 単位で `describe` を立てる**（`describe("TaskStatusMismatchError")`）。モデルのファイルにエラー class があるなら、そのモデルのテストファイルに、公開 API のキー単位の `describe` と、エラー class 単位の `describe` が並ぶ。エラー class 単位の `describe` はファイルの末尾に置く。
インターフェースの実装は、実装名とメソッド名で立てる（`describe("TaskRepositoryImpl.get")`）。

**`test` を使い、`it` は使わない。** テスト名は日本語で「条件なら結果」と書く。
失敗を確かめるテストは、名前にエラーの class 名を入れる。実行結果の一覧だけで、どの種別を期待したかが読める。
例外は、種別を Then で確かめない副作用のテスト（表題が空ならクロックを呼ばない、など）で、class 名を入れない。
名前に入れると、確かめていない種別を確かめたように読めてしまう。

**テスト名は `正常系: ` `異常系: ` `不変性: ` `型: ` のどれかで始める。** テストの観点が実行結果の一覧に出て、
どの観点が薄いかが読める。`describe` を観点で入れ子にはしない。階層が増えるだけで、同じことが読めるからである。

| 接頭辞 | 入れるもの | 振り分け |
|---|---|---|
| `正常系: ` | 例外が出ずに、期待どおりの値が返る | 受け入れる境界値、戻り値の中身、完成値スキーマの検証を通るかどうか、等価性の判定 |
| `異常系: ` | 対象操作が例外で終わる（`Promise` なら reject する） | 拒否する境界値、失敗の種別と `operation`、失敗時に依存を呼ばないこと、クライアントの失敗の伝播 |
| `不変性: ` | 呼んでも、返した値も渡した値も壊れない | 結果の凍結、入れ子の凍結、引数を変えないこと、無変更なら同じ参照を返すこと |
| `型: ` | 型検査が拒否する（`Xxx.test-d.ts` のテスト） | 生の値をブランド付きの項目に渡せない、別種の識別子を渡せない |

**振り分けは「対象操作が例外で終わるか」だけで決める。** 入力が不正かどうかでは決めない。
完成値スキーマの `safeParse` が不正な値に失敗を返すのは、例外が出ないので正常系である。
**既存のプロジェクトが失敗を例外ではなく `Result` で返すなら、失敗（`err`）で終わるテストは例外で終わるものとみなして `異常系: ` にする。**
その `Result` は、このスキルの `create` が投げる例外の代わりだからである。完成値スキーマの `safeParse` が返す失敗は、`Result` の方式でも正常系のままにする。
`*.test-d.ts` の型のテストは `型: ` で始める。実行時に終わり方を持たないので、ほかの3つとは別に扱う。

**`describe` の中は、正常系 → 異常系 → 不変性 の順に並べる。** 観点ごとに固まるので、
どの観点が薄いかが読むだけで分かる。同じ接頭辞の中の並びは、対象ファイルの制約の並びに合わせる。

観点が1つしか無い `describe`（完成値スキーマの検証だけなど）でも、ほかの接頭辞を無理に作らない。
「異常系が無い」ことがそのまま契約の形を表す。

**テスト名は述語で終える。体言止めにしない。** `test("正常系: 小文字を含むなら InvalidCreationParamError")` のように
class 名や `true` で終えると、結果が起きることなのか返る値なのかが名前から読めない。
`が発生する`（例外）、`と判定される`（等価性・比較）、`検証を通る` `検証を通らない`（完成値スキーマ）、`になる` `を返す`（戻り値）で終える。
条件の側も、何の操作に対する条件かが分からないなら補う（`失敗したら` ではなく `create に失敗したら`）。

**条件が無いなら、結果だけを書く。引数そのものを `〜なら` の条件にしない。**
`test("正常系: ProjectId と件数なら番号の大きい順に上限件数を取る Query を送信する")` の
`ProjectId と件数なら` は、その操作が必ず受け取る引数を並べただけで、何も切り分けていない。
`〜なら` は、同じ操作の中で結果が分かれるときに書く（`応答に Item が無いなら`、`余剰キーを持つなら`、
`完了時刻が着手時刻と同じなら`）。分かれないなら `test("正常系: 番号の大きい順に上限件数を取る Query を送信する")`
と結果だけを書く。渡すものは `// Given:` が述べているので、名前に書くと同じことが2箇所に出る。
`DTO なら` `入力なら` `保存値なら` のように、引数の種類だけを条件にしない（`from` は必ず DTO を受け取る）。
`test("正常系: backlog の DTO なら対応する Task に戻る")` は `test("正常系: backlog の DTO は対応する Task に戻る")` と書く。
`制約を満たす入力なら` のように、同じ操作の失敗と結果を分ける条件が付いていれば書いてよい。

**テストの作り方ではなく、対象の振る舞いを書く。** `書き下ろした DTO` `DTO と同じ保存キー` のように、
その値をテストがどう用意したか、どこと突き合わせたかを名前や説明に出さない。
`DTO と同じ保存キーとテーブル名で Get を送信する` は、期待値を DTO から作らないという規則と食い違ううえ、
`get` が何をするのかを述べていない。`受け取った TaskId から保存キーを組んで Get を送信する` と、
対象が入力をどう扱うかで書く。**`仕様どおりの` も、それ自体は何も述べていないので避ける**
（`カウンタを1増やす Update を送信する` のように、実際の振る舞いを書く）。
Then の `期待する値の` も同じで、テーブルの `expected` 列を言い換えただけである。
`// Then: 各項目が期待する値の Task になる` ではなく、`// Then: その DTO の各項目を持つ Task と一致する` のように、何が一致するかを書く。
例外の結果は `が発生する` に統一し、`が投げられる` とは書かない。Then のコメントも同じ語で書く。

```ts
test("異常系: 小文字を含むなら InvalidCreationParamError が発生する", () => { /* ... */ });
test("異常系: create に失敗したら operation が ProjectId.create の InvalidCreationParamError が発生する", () => { /* ... */ });
test("正常系: バックログの Task は着手できる", () => { /* ... */ });
```

`describe` の並びは、対象ファイルのセクションの並び（生成 → 復元 → 等価性 → 読み取り → 比較 → 業務操作 → 演算 → 変換）に合わせる。完成値スキーマの `describe` は、復元のあとに置く。

## 1つのテストで確かめること

**1つのテストは、1つの前提のもとで、1つの対象操作について、1つの契約を確かめる。**
契約とは、仕様として単独で説明できる期待結果である。`expect` の個数では数えない。

同じ戻り値や同じ例外を説明するために、`expect` を複数書いてよい。
独立に変わりうる契約は、同じ操作でもテストを分ける。

| 1つのテストにまとめてよい | 分ける |
|---|---|
| **捕まえた例外の**種別と `operation` | 完了できる / 元の Task を変えない / 結果が凍結される |
| 着手後の Task 全体が期待値と一致する | `create` が失敗する / `reconstruct` が失敗する（操作が違う） |
| | バックログの Task を DTO に変換して戻すと元に戻る / 完了した Task を DTO に変換して戻すと元に戻る（前提が違う。テーブル駆動にする） |
| **エラー class の、引数を素で写した項目どうし（`operation` / `taskId` / `expected` / `limit` など）** | **エラー class の `issues` / `cause` / `name`（決まり方が違う）** |
| | **結果が凍結される / 入れ子の配列が凍結される / 配列の要素が凍結される**（凍結はそれぞれ別の `.readonly()` で決まり、1階層ずつしか効かない。実物は `example/domain/entity/Task.test.ts` の `Task.addComment` の不変性） |

**対象操作は1回だけ呼ぶ。** DTO に変換してからドメインに戻す（`to` のあと `from`）ように、複数回の呼び出しそのものが契約なら例外とする。

### 境界値をどこで確かめるか

**細かい境界値は `create` で確かめ、`reconstruct` は成功1つと代表の失敗1つにする。**
2つは同じ完成値スキーマを通るので、境界を両方に書き写しても新しく止まる実装がない。

`reconstruct` だけの約束（渡された並びのまま受け入れ、並べ替えないなど）があるなら、成功の1つはそれを示す保存値にする（`Labels.reconstruct` の昇順でない保存値）。

**キーを持つ値（オブジェクトのスキーマ）では、代表の失敗を余剰キーを持つ保存値の拒否にする。** 同じテストで、種別が `InvalidReconstructParamError` で `operation` が `"Xxx.reconstruct"` になることを確かめる
（`test("異常系: 余剰キーを持つなら operation が Task.reconstruct の InvalidReconstructParamError が発生する")`）。
余剰キーはどの項目の制約にも依らないので、`create` で確かめた境界値を写さずに失敗を起こせる。
余剰キーを持ちえない値（1つの値を包む値オブジェクト、配列のコレクション）では、制約に違反する値1つで種別と `operation` を確かめる代表の失敗にする。

**`create` で確かめた境界値（空文字・上限・件数・重複など）は `reconstruct` に写さない。** `create` に渡せる値なら、`create` のテストがすでに止めている。
**導出値の上限も `create` の境界である。** 「明細の合計が上限を超える」は、1つ1つは有効な明細の組み合わせを `create` に渡せば起こせるので、`create` で確かめ、`reconstruct` には写さない。
導出値について `reconstruct` で確かめるのは、保存された導出値が依存元から計算した値と食い違う不整合だけである（`create` は導出値を自分で計算するので、この値を渡せない）。
`reconstruct` で足して確かめてよいのは、成功でも失敗でも、`create` では渡せない値だけである（`create` が組まない状態ごとの成功や、状態の不変条件の境界で受け入れることなど）。
**`create` では作れない値で `reconstruct` の成功を確かめるときは、なぜ `create` で作れないかを `// Given:` に書き、値がその理由どおりかを計算して確かめる。**
割引率を整数パーセントで受け取る `create` に対して「割引額が合計の整数パーセントに当たらない」保存値を使うなら、割引額7円・合計1000円のように、どの整数パーセントにも当たらない値にする
（割引額80円・合計1000円は8%なので `create` で作れ、2つ目の通常の成功になる）。
Given は `// Given: create は整数パーセントの割引しか組まないので作れない、割引額7円・合計1000円の保存値で` のように書く
（実物は `example/domain/entity/Task.test.ts` の `Task.reconstruct` の「着手時刻が作成時刻と同じ」）。

| `create` では渡せない値 | 例 |
|---|---|
| ブランドや列挙の型が `create` の引数で止める値（下を参照） | 形式違反の識別子（`Comment.create` は ID を受け取らず、`Project.create` はブランド付きの `ProjectId` を受ける） |
| `create` が組まない状態や、状態の不変条件を破る値 | バックログなのに `startedAt` を持つ、着手時刻が作成時刻より前、投稿順でない `comments` |
| 依存から取るので `create` の引数に無い項目の値 | 負の作成時刻 |
| `create` が計算する導出値の、依存元との食い違い | 明細の合計と食い違う合計額（導出値の上限を超える組み合わせは `create` に渡せるので当たらない） |
| `create` は受け入れて並べ替えるが、`reconstruct` は拒否する値 | 並び順を固定したコレクションの、決めた順でない保存値（`SKILL.md` の規則5） |

### 型が止める不正な値

**ブランド付きの項目や列挙の外の値のように、`create` の引数の型が受け付けない不正な値は、`as` でも `@ts-expect-error` でも `create` に渡さない。**
実行時にその制約が効いていることは、生の値を受ける `reconstruct` か、`unknown` を受ける完成値スキーマの `safeParse` で確かめる。
型で止まることそのものは型のテスト（`references/test-style-type-tests.md`）で確かめる。

## Given / When / Then

**すべてのテストに `// Given: 説明` `// When: 説明` `// Then: 説明` をこの順で書き、セクションを空行で区切る。** Then の中だけ、条件を満たすときに `// And: 説明` で分ける（下を参照）。

| セクション | 置くもの | 説明に書くこと |
|---|---|---|
| Given | 対象操作に渡すもの。入力と依存 | 前提の状態（「〜があるとき」） |
| When | 対象操作の実行。例外を受ける変数もここに置く | 起きる出来事（「〜すると」） |
| Then | 期待値の組み立てと検証。対象操作は呼ばない | 期待する結果（「〜が発生する」「〜と一致する」） |

準備が要らなくても `// Given:` は残す。コメントを埋めるためだけの変数は作らない。

### 説明の書き方

**コロンのあとに、そのセクションで何をしているかを1行で短く書く。** 形式は `// Given: 説明`（半角のコロンと空白）。句点は付けない。

**Given から Then までを続けて読むと1つの文になるように書く。** Gherkin の「前提 / もし / ならば」に合わせる。

| コメント | 書くこと | 文の終わり | 例 |
|---|---|---|---|
| `// Given:` | 前提の状態、または対象操作に渡すもの | 「〜があるとき」「〜であるとき」、渡すものだけなら「〜で」 | 小文字を含む ProjectId の入力があるとき |
| `// When:` | 起きる出来事 | 「〜すると」 | その ProjectId を生成すると |
| `// Then:` | 期待する結果 | 結果の状態（「〜が発生する」「〜と一致する」「〜と判定される」「〜が返される」「〜になる」） | InvalidCreationParamError が発生する |

続けて読むと「小文字を含む ProjectId の入力があるとき、その ProjectId を生成すると、InvalidCreationParamError が発生する」になる。

**1行の説明で分かりやすく言えるなら、1行で書く。** 前提や確かめることが複数あっても、`// Then: 操作名が ProjectId.create の InvalidCreationParamError が発生する` のように1行で読めるならそれでよい。

**説明は1行で書く。`// And: 説明` で分けるのは、次の1つの場合だけである。** Gherkin の And に合わせる。

> **対象操作が投げた例外を受けて、その種別に加えて例外の項目を2つ以上確かめるとき。** `// Then:` に種別を、`// And:` に項目を書く。

種別と項目は独立して壊れるので、説明を分けると、どちらが落ちたかが読める。

**エラーを直接作って項目を見るテスト（エラー class のテスト）では使わない。** `new InvalidCreationParamError(…)` で
作った値の `operation` や `issues` を確かめるのは、例外が投げられていないので正常系である。
確かめる種別が無く、項目だけが並ぶので、分ける先が無い。`// Then:` 1行に書く。
基底 class と `Error` の両方のインスタンスであることも、`expect` を2つ並べて1行の説明で書く
（`// Then: 業務エラーの基底 class と Error の両方のインスタンスになる`）。
実物は `example/domain/shared-errors.test.ts` にある。
**判定は「Then に種別の `expect` があるか」と「確かめる項目が2つ以上か」の2つだけで決める。**
`expect` の個数では決めない。項目を `toMatchObject` で1つの `expect` にまとめても、
中の項目が2つ以上なら分ける（実物は `example/domain/entity/Task.test.ts` の `Task.start` の異常系）。

| Then の中身 | 書き方 |
|---|---|
| 種別の `expect` + 項目2つ以上 | `// Then:` に種別、`// And:` に項目 |
| 種別の `expect` + 項目1つ | **1行**（`// Then: 操作名が Comment.create の InvalidCreationParamError が発生する`） |
| 種別の `expect` が無い（エラー class のテスト、戻り値の検査） | **1行**（`// Then: 操作名と左辺・右辺の単位が渡した順のまま残っている`） |
**Given では使わない。** 前提が2つあっても1行に並べる（`// Given: バックログ以外の状態の Task と、担当者と着手時刻で`）。

- `// And:` は、その assertion のコードの直上に置く。前に空行を置かず、Then の続きであることを見せる
- **When には使わない。** 対象操作は1回だけ呼ぶので、When に書く出来事は1つしかない
- Then を And で分けたときは、`// Then:` の行を「〜が発生し」と文をつなぐ形で終え、`// And:` の行を結果の状態で終える。Given から Then まで続けて1つの文として読める
- 独立に変わりうる契約を And でつないで1つのテストにしない（「1つのテストで確かめること」を参照）

**落ちるのはほぼこの2つである。** 同じファイルの中で片方だけ間違えることが多い。

```ts
// ✗ 確かめている項目が operation の1つだけなのに And で分けている
// Then: TaskStatusMismatchError が発生し
expect(caught).toBeInstanceOf(TaskStatusMismatchError);
// And: 操作名が Task.start である
expect(caught).toMatchObject({ operation: "Task.start" });

// ✓ 項目が1つなら1行にまとめる
// Then: 操作名が Task.start の TaskStatusMismatchError が発生する
expect(caught).toBeInstanceOf(TaskStatusMismatchError);
expect(caught).toMatchObject({ operation: "Task.start" });

// ✗ エラー class のテストで使っている（例外を投げていないので種別の検査が無い）
// Then: 操作名が残り
expect(error.operation).toBe("Task.create");
// And: cause に元の ZodError を持つ
expect(error.cause).toBe(cause);

// ✓ エラー class のテストでは And を使わない。operation の保持と cause の保持は
//    決まり方が違うので別のテストにし、それぞれ Then 1行で説明する
```

| コメント | 置く場所 | 途中の行の終わり | 最後の行の終わり |
|---|---|---|---|
| `// Given:` | Given の中（1行だけ） | — | 「〜があるとき」、渡すものだけなら「〜で」 |
| `// When:` | When の中（1行だけ） | — | 「〜すると」 |
| `// Then:` / `// And:` | Then の中 | 「〜が発生し」「〜と一致し」 | 結果の状態 |

- **名詞で止めない。** `// Given: 小文字を含む ProjectId` のような名詞だけの行と、`// When: 生成する` のような動詞で終わる行を混ぜると、読み手が行ごとに文の型を読み替えることになる
- When と Then では、Given で出てきたものを「その」「それ」で指す
- **Given が対象操作に渡すものだけなら「〜で」で終える。** 前提の状態を述べるなら「〜があるとき」。「で」で終えたときは、When で渡すものを言い直さず、操作だけを書く（`// Given: 制約を満たす入力と固定の時刻を返すクロックで` → `// When: Task を生成すると`）。When が `その〜` で言い直す形のままなら、Given は「〜があるとき」にする
- 準備が要らないテストでも、`// Given: 特別な前提が無いとき` と前提の状態を書く
- 例外を捕まえる When も、捕まえることは書かず「〜を試みると」と書く。例外が起きることは Then に書く。型のテストの When は、型が拒否するコードの書き方をそのまま述べる。`create` の第1引数や操作のパラメータオブジェクトなら「〜を入れて `Xxx.create` を呼ぶと」「〜を入れて `Xxx.start` を呼ぶと」、class のコンストラクタ引数なら「〜を渡すと」
- **`result` や `expected` のような変数名を説明に出さない。** `// Then: 結果は…` ではなく、できあがったモデルの状態で書く（`// Then: 凍結された Task になる`）。変数名はテストコードの都合で、確かめている契約ではない
- **期待値は Then で組み立てる。** Given に置くと、前提なのか確かめたい結果なのかが混ざる。`const expected = …` は `// Then:` の直下に置き、その下で比べる。
  テーブル駆動では、行ごとに違う期待値を行のデータとして持たせ、Then でその値と比べてよい。行の外で `const expected` を Given に置くのは、テーブル駆動でも避ける
- **テストコードの都合は説明に書かない。** 例外を受ける変数（`let caught: unknown;`）は When の `try` の直上に置き、説明には出さない。ヘルパーで作ったことも書かない（`// Given: 制約を満たすダミーの CommentId があるとき` ではなく `// Given: 制約を満たす CommentId があるとき`）。Given には確かめる前提だけを書く
- **ヘルパーの既定値と比べた言い方もしない。** `既定の依存で` `既定と違う ProjectId を持つ Task で` は、ヘルパーを読まないと意味が通じない。
  その値が何であるかを、確かめることに関わる性質で書く（`制約を満たす時刻を返すクロックで`）
- 業務の言葉で書く。リテラルを書き写さず、その値の意味を書く。`// Given: "proj" があるとき` ではなく `// Given: 小文字を含む ProjectId の入力があるとき`
- **定数や API の識別子は訳さず、そのまま書く。** `Number.MAX_SAFE_INTEGER` を「安全な整数の上限」と書かない。訳すと、テスト名に書いた識別子と説明が食い違い、どの値の境界を確かめたのかが読めなくなる
- **渡すものの呼び名を、対象操作ごとに固定する。** 同じファイルの中で呼び名が揺れると、どの段階の値を渡しているのかが読めなくなる

| 対象操作 | 渡すものの呼び名 | 例 |
|---|---|---|
| `create` | **入力**（1つの値やコレクションをそのまま渡すモデルも同じ。モデル名を添えて「〜の入力」と書く） | `制約を満たす Estimate の入力で`、`制約に違反する ProjectId の入力があるとき` |
| `reconstruct` | **保存値**（正常・異常を問わない） | `制約を満たす Estimate の保存値で`、`1項目だけ制約に違反する保存値で` |
| 等価性・業務操作・演算 | モデル名（完成値を渡すので） | `制約を満たす Estimate があるとき` |
| **完成値スキーマの検証を通らない側** | **モデル名を添えて、何が違うかを述べる** | `型が違う値があるとき`、`制約に違反する Estimate の保存値があるとき` |

**完成値スキーマの拒否のテーブルで「不正な値」と書いてしまう例が多い。**
同じファイルの `reconstruct` の拒否テーブルは「形式違反の貸出番号」と書けているのに、
完成値スキーマのテーブルだけ揃わない、という形で出る。完成値スキーマは `unknown` を受けるので
渡すものの呼び名が決まって見えないが、**ここでも「何が違うか」を述べる。**

- **その値が何に使われるかを書く。値自身を動作主にしない。** 対象操作に `cause` として渡す `ZodError` は
  `原因に渡す ZodError` と書き、`原因として包む ZodError` とは書かない。包むのは受け取る側のエラーであって、渡す値ではない
- **列挙の値は「定義に含まれる」「定義に無い」で対にして述べる。** `定義済みの` とは書かない。「済み」は何かが終わった時点を指す言い方で、
  値が列挙に載っているかどうかという静的な話とずれる。同じ条件の肯定と否定で言い方が変わると、対になっていることが読めなくなる
- **違反の内容を述べたなら、「不正な」を重ねない。** `番号が下限より1小さい保存値` と書き、`番号が下限より1小さい不正な保存値` とは書かない。
  何が違反しているかを述べられないテーブル駆動では、`制約に違反する〜` と書く（`不正な〜` とは書かない）
- テスト名の言い直しで済ませない。テスト名は条件と結果を、説明はそのセクションの中身を書く
- 目安は40字まで。長くなるなら、そのセクションに詰め込みすぎている。ただし、確かめている class 名・操作名・識別子は、40字を超えても省かない。「生成の失敗を表す種別と操作名を持つ例外になる」のように意味だけに言い換えると、何を確かめたのかが説明から消える。`// Then: 操作名が ProjectId.create の InvalidCreationParamError が発生する` と具体名で書く

**コードを読めば分かることでも書く。** 何をしているかのコメントは、コードを読めば分かり、実装と食い違う危険があるので書かないのが通例だった。
テストでは次の理由で書く。

- AI が出力したテストをレビューするとき、コードを読む前に各セクションの意図を拾え、読む速度が上がる
- 意図と中身の食い違いそのものが、レビューで見つけるべき誤りの手掛かりになる
- 食い違いの危険は、完了の確認（`references/checklist.md`）で説明とコードの一致を確かめることで抑える

**テストを直したら、説明も同じ変更で直す。** 説明がそのセクションのコードと食い違っていたら、テストの誤りとして扱う。

```ts
describe("Estimate.equals", () => {
	test("正常系: 大きさも単位も同じなら等しいと判定される", () => {
		// Given: 大きさも単位も同じ2つの Estimate があるとき
		const a = createDummyEstimate({ amount: 3, unit: "point" });
		const b = createDummyEstimate({ amount: 3, unit: "point" });

		// When: その2つの Estimate の等価性を判定すると
		const result = Estimate.equals(a, b);

		// Then: 等しいと判定される
		expect(result).toBe(true);
	});
});
```

### When と Then がくっつくとき

**matcher が対象操作を実行する場合は、`// When:` と `// Then:` を空行を挟まずに並べる。** 両方に説明を付ける。
2つで1つのセクションだと見て分かるようにする。例外を期待する `toThrow` がこれに当たる。

```ts
describe("ProjectId.create", () => {
	test("異常系: 小文字を含むなら InvalidCreationParamError が発生する", () => {
		// Given: 小文字を含む ProjectId の入力があるとき
		const value = "proj";

		// When: その ProjectId を生成すると
		// Then: InvalidCreationParamError が発生する
		expect(() => ProjectId.create(value)).toThrow(InvalidCreationParamError);
	});
});
```

**セクションを分けるためだけに `const act = () => ProjectId.create(value)` を作らない。**
関数を作っても実行されるのは Then の中なので、When に「実行」を置くという定義と食い違う。

型のテストも、実行する操作が無いので同じ形になる（`references/test-style-type-tests.md`）。

### 例外の中身を見るとき

種別のほかに `operation` や分岐用のフィールドを確かめるなら、When で1回だけ捕まえて、Then で見る。受け皿の `let caught: unknown;` も When の `try` の直上に置く。
`catch` の中に `expect` を置かない。対象が例外を投げなかったとき、`catch` の中の `expect` は1つも実行されず、テストが何も確かめずに通る。

```ts
describe("Task.start", () => {
	test("異常系: バックログでないなら期待した状態と実際の状態を持つ TaskStatusMismatchError が発生する", () => {
		// Given: 完了した Task と、担当者と着手時刻があるとき
		const task = createDummyDoneTask();
		const params = { assigneeId: createDummyUserId(), at: createDummyTimestamp(3_000) };
		// When: その Task の着手を試みると
		let caught: unknown;
		try {
			Task.start(task, params);
		} catch (error) {
			caught = error;
		}

		// Then: TaskStatusMismatchError が発生し
		expect(caught).toBeInstanceOf(TaskStatusMismatchError);
		// And: その例外は操作名 Task.start と、その Task の識別子と、期待した状態 backlog と実際の状態 done を持つ
		expect(caught).toMatchObject({
			operation: "Task.start",
			taskId: task.id,
			expected: "backlog",
			actual: "done",
		});
	});
});
```

例外が投げられなければ `caught` は `undefined` のままなので、1行目の `toBeInstanceOf` で落ちる。

### 非同期のとき

失敗を確かめるときは、When で Promise を受け取り、Then で `await` する。
成功を確かめるときは、When で `await` して結果を受け取る（`// When: 採番すると` の下に `const result = await issuer.next(projectId);`）。

**`Promise` が reject する結果も `が発生する` と書く。** `で失敗する` とは書かない。同期と非同期で語を変えない。
これは Then に書く**結果**の語である。Given でクライアントの性質を述べる `例外で失敗するクライアントで` は対象外とする。

```ts
// When: 採番を始めると
const pending = issuer.next(projectId);

// Then: InvalidTaskNumberResponseError が発生する
await expect(pending).rejects.toThrow(InvalidTaskNumberResponseError);
```

`rejects` / `resolves` は必ず `await` する。Vitest 5.0.1 は付け忘れた assertion を、中身が通るものでも
「was not awaited」としてそのテストの失敗にする（実測）。Jest は待たないので、付け忘れるとテストが先に終わって通る。

## テーブル駆動

**テーブル駆動にしてよいのは、次をすべて満たすときだけである。**

1. すべての行が、同じ公開操作の同じ契約を確かめる
2. Given の組み立て、When の呼び出し、Then の matcher が共通で、行ごとの違いをデータだけで表せる
3. 行によって処理を切り替える分岐が無い
4. 各行が独立していて、ほかの行の結果にも実行順にも依存しない
5. 展開後のテスト名だけで、どの入力の何を期待したかが分かる

成功と例外は別のテーブルにする。**例外を期待するテーブルには、同じ操作が同じ具象の class を投げる行だけを入れる。**
行によって違反する制約（長さと文字種など）が異なるのはよい。制約ごとに表を分けると1行だけの表が並び、読みやすくするという目的に反する。
投げる class が異なる行（`InvalidCreationParamError` と `EstimateUnitMismatchError`）は分ける。
期待値が行によって `true` と `false` に分かれるのは、同じ契約なら1つのテーブルでよい。

行の値をヘルパーで作ると、テストの収集時に `describe` の中で実行される。そこで例外が出ると、
テスト単位ではなくファイル全体の収集エラーとして報告される。

**書き方は `test.for` と、オブジェクトの行と、`$プロパティ名` のテスト名だけを使う。**

```ts
describe("ProjectId.create", () => {
	test.for([
		{ name: "小文字を含む", value: "Proj" },
		{ name: "1文字", value: "P" },
		{ name: "11文字", value: "ABCDEFGHIJK" },
		{ name: "数字を含む", value: "PROJ1" },
	])("異常系: $name なら InvalidCreationParamError が発生する", ({ value }) => {
		// Given: 制約に違反する ProjectId の入力があるとき

		// When: その ProjectId を生成すると
		// Then: InvalidCreationParamError が発生する
		expect(() => ProjectId.create(value)).toThrow(InvalidCreationParamError);
	});
});
```

テスト名の `$name` は `'小文字を含む'` のように引用符付きで表示される（実測）。そのまま受け入れる。
テーブル駆動の `// Given:` には、行から受け取る値の意味を書く。その文だけでは行によって何が変わるかが分からないときに限り、「ケースごとの〜があるとき」と書く。

**行の型が広がって代入できないときは、`test.for` に行の型を型引数で渡す。** `status: "backlog"` のような
リテラルは、配列の要素として推論されると `string` に広がり、`TaskSchemaInput` に代入できない。
`as` で狭めず、`test.for<Readonly<{ name: string; input: TaskSchemaInput }>>([ … ])` と書く。
行によって持つ項目が異なり `{ PK: string } | { SK: string }` のような型に推論され、ヘルパーの引数に代入できず型エラーになるときは、
上書きの引数を行に持たせず、ヘルパーを呼んで組み立てた値そのものを行に持たせる。

**`test.each` は使わない。** 違いは次のとおり。

| | `test.for` | `test.each` |
|---|---|---|
| 配列の行 | 展開せずに1つの引数で渡す（`([a, b]) => …`） | 位置引数に展開する（`(a, b) => …`） |
| 第2引数 | TestContext（テストごとの `expect`、fixture） | 無い |
| オブジェクトの行、`$prop` と `%s` の書式、テンプレート文字列の表 | 使える | 同じく使える |
| 位置付け | Vitest が新しいコードに勧めている | Jest 互換のために残されている |

**テストの中で `for` や `forEach` を回して、複数のケースを確かめない。**
1件目で落ちると残りが実行されず、どの行が落ちたかもテスト名に出ない。
上限件数の配列を作るような、1つのケースのデータを組み立てるループは Given に置いてよい。

## assertion の選び方

| 確かめたいこと | 使う | 使わない |
|---|---|---|
| 成功したこと | 戻り値の値 | `not.toThrow()` |
| 例外の種別 | `toThrow(具象の class)` | `toThrow()`（引数なし）、`toThrow(DomainError)`、`toThrow(Error)`、`not.toThrow(別の種別)` |
| 例外の中身 | When で捕まえて `toBeInstanceOf` と `toMatchObject` | `catch` の中の `expect` |
| オブジェクトや配列の一致 | `toStrictEqual` | `toEqual` |
| 同じ参照か | `toBe` | |
| キーが無いこと | `expect("startedAt" in result).toBe(false)` | `toBeUndefined()`（キーが残って値が `undefined` でも通る） |
| 呼ばれていないこと | `vi.fn` と `not.toHaveBeenCalled()` | 手書きのカウンタ |

`toThrow(class)` は `instanceof` で判定するので、兄弟の class を投げれば落ちる（実測）。
基底の `DomainError` を渡すと、どの業務エラーでも通るので種別を確かめたことにならない。
`not.toThrow(別の種別)` は、何も投げない誤実装も通すので書かない。種別どうしが混ざらないことは
エラー class のテストで、具象の直接の親が `DomainError` であることを確かめる（`references/testing-errors.md`）。

`toEqual` は `{ a: 1, b: undefined }` と `{ a: 1 }` を等しいとみなす（実測）。
このスキルは「状態に無い項目はキーごと落とす」ので、それを検出できない matcher は使わない。
