# 完了の確認: モデル

`references/checklist.md` の項目と合わせて確かめる。確認するのは、対象に該当し、今回採用した規約で有効な項目だけである（適用の考え方は `SKILL.md` の「完了の確認」）。

- [ ] 完成値スキーマが受理する値について、入力と出力が同じである（`z.url()` のように暗黙に変える API を使うなら、変わる入力を手前の `refine` で拒否している。`z.url()` なら前後の空白と途中の改行・タブ・CR。書き換えずに受理してしまう制御文字・`\`・途中の空白も拒否している）
- [ ] 列挙（`z.enum`）を除く値オブジェクトとエンティティの完成値スキーマに、ブランドを付けている（check.mjs の `brand-symbol` は付け方だけを見て、付けたかは見ない）
- [ ] 〔check.mjs〕ブランドが `unique symbol` で、記号を export していない
- [ ] 〔check.mjs〕エンティティのブランドが出力側だけに付いている
- [ ] create の第1引数の作り方を判定表の上から見て、最初に当てはまった行を使っている
- [ ] #1（1つのプリミティブ値を包むモデル）以外のすべてに `CreateXxxPropsSchema` がある
- [ ] `CreateXxxPropsSchema` に `.readonly()` が付いている
- [ ] #2〜#4 の `create` が `props` の検証と完成値の検証を順に行い、完成値スキーマには第1引数の検証の成功結果を渡している（#1 は完成値スキーマの1回だけ）
- [ ] #2〜#4 では、`props` をそのまま完成値スキーマに渡せるモデルでも、第1引数の検証を省いていない
- [ ] #2 が `z.strictObject(XxxFields).pick({...})` で派生している（`unwrap().pick()` や独立定義になっていない）
- [ ] #3 のコレクションが完成値と同じ要素のスキーマを使い、件数・重複（並び順を固定したなら順序も）の検証を完成値スキーマに残している
- [ ] #4 でも項目のスキーマを再利用している（`PrioritySchema` を書き直していない）
- [ ] 完成値に残らない項目 (e) と、その項目どうしの制約を第1引数のスキーマで検証している
- [ ] `CreateXxxProps` の型を第1引数のスキーマの `z.output` から取っている（`XxxSchemaInput` から取っていない）
- [ ] `create` の第1引数が、既存のドメイン値を受け取る項目にそのドメイン型を要求している（生の値をコンパイルで止める）
- [ ] `XxxSchemaInput` の型を `z.input` から取っている（単一プリミティブの値オブジェクトには作らない）
- [ ] create の第1引数が `strictObject`（コレクションは `array`）で、自動で決まる項目と既定値を含まない
- [ ] `.extend()` / `.omit()` / `options[n]` の添字で create の第1引数を作っていない
- [ ] `createXxx` が入力検証 → 入力だけで決まる導出 → 生成器 → 生成器の戻り値を使う導出 → 完成値検証の順で組み立てている（無い段は飛ばす）
- [ ] `createXxx` が生成器の戻り値を、取った直後に完成値と同じ項目のスキーマで確かめ、不正なら `InvalidClockValueError` / 識別子の型ごとの class（`InvalidGeneratedCommentIdError` など） を投げている。生成器そのものが投げた例外は包まずに伝えている
- [ ] `createXxx` の末尾の完成値の検証の種別を、そこに着く原因が残っているかで決めている（入力だけで違反しうる検査があれば `InvalidCreationParamError`、無ければ `FatalUnreachableError`）
- [ ] 〔check.mjs〕`parse` / `safeParse` にキーを持つオブジェクトリテラルを渡している箇所すべてに `satisfies XxxSchemaInput` が付いている（配列リテラルには付けない）
- [ ] 横断検証から例外を投げうる関数を呼んでいない
- [ ] 横断検証から呼ぶ導出関数が、導出できないときに例外を投げず `undefined` を返している
- [ ] `reconstructXxx` が欠損補完も再採番もしない
- [ ] 〔check.mjs〕`value is Xxx` を返す関数（型ガード）が1つもない。既存の完成値を状態で絞る述語も書いていない
- [ ] 複数値の値オブジェクトに等価性の関数がある（単一値の値オブジェクトに置くことは禁じていない。置くかは利用側の必要で決める）
- [ ] コレクションの空・最大件数・重複・順序を決めている（依頼に無い最大件数は置かず、要否を回答で確認している）

- [ ] 順序に意味のないコレクションを `create` で並べ替えるとき、並べ替え以外（重複の除去・値の書き換え）をしておらず、`reconstruct` は並べ替えていない
- [ ] 状態別ユニオンでないモデルに `XxxCommonFields` を作っていない（`pick` の派生元として切り出す `XxxFields` はこれに当たらない）
- [ ] 状態に無い項目と任意項目を、分割代入または条件付きスプレッドでキーごと落としている（`undefined` を代入していない）
- [ ] 業務操作が第1引数に対象、第2引数にパラメータオブジェクト（生成器を使うなら第3引数に依存）を取り、前提条件が関数冒頭の `if` で書かれている
- [ ] 子エンティティを集約ルートの業務操作の中で作っている（アプリケーション層に子の `create` を呼ばせていない）
- [ ] 集約が持つ値オブジェクトやコレクションを変える操作を、集約ルートの業務操作として置いている（利用側にスプレッドで組み立てさせていない。依頼で求められた操作について）
- [ ] 業務操作に Zod スキーマを置いていない（スキーマは完成値と create の第1引数の2つだけ）
- [ ] 値オブジェクトに切り出していない項目を書き換える業務操作が、完成値と同じ項目のスキーマで引数を確かめ、失敗を何が起きたかを表す名前のエラーに包んでいる（制約を操作の側に書き写していない）
- [ ] 業務操作だけが持つ引数の条件（使うポイント数は1以上の整数など）を、関数冒頭の `if` で確かめ、その規則だけを表す名前のエラーで拒否している（引数用の値オブジェクトを作って `InvalidCreationParamError` に任せていない。規則が違えば class を分けている。`references/model-code.md`「業務操作で Zod を使わない」）

- [ ] `create` の入力の不正が `InvalidCreationParamError`、生成器が返した値の不正が `InvalidClockValueError` / 識別子の型ごとの class（`InvalidGeneratedCommentIdError` など）、`reconstruct` の失敗が `InvalidReconstructParamError`
