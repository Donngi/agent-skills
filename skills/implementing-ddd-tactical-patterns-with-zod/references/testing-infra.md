## インフラ: DTO と保存キー

### DTO との対応

**変換して戻すと元に戻ることを確かめるだけでは、誤実装を検出できない。** `to` と `from` の両方で同じ項目を取り違えた実装は、どちら向きに変換して戻しても元に戻る。
先に、仕様から独立に書き下ろした DTO との対応を確かめる。

- [ ] **全状態で**、`to` の結果が、独立に書いた DTO と `toStrictEqual` で一致する
- [ ] コレクションや入れ子を持つなら、要素ごとに値の違う空でないコレクションでも、`to` と `from` のそれぞれが独立に書いた DTO と対応する（空のコレクションだけでは、要素の項目の取り違えを検出できない）
- [ ] **全状態で**、独立に書いた DTO を `from` した結果が、ダミーで組んだ完成値と一致する
- [ ] 任意項目や状態に無い項目が、DTO でもキーごと無い

### 変換して戻すと元に戻る

- [ ] **全状態で** ドメイン → 保存 → ドメイン が一致する（状態を行にしたテーブル駆動）
- [ ] **全状態で** 保存 → ドメイン → 保存 が一致する（いま書き込んでいる形式で、表現を変えずに読み書きする値の場合）
- [ ] 旧形式の読み取りや DTO の変換があるなら、保存 → ドメインが期待する完成値になり、それをもう一度保存すると、いまの DTO になる。旧い保存値そのものと一致することは求めない。期待値は変換関数から作らず独立に書く

```ts
describe("fromDynamoDBTaskItemDTO", () => {
	test.for([
		{ name: "backlog", task: createDummyBacklogTask() },
		{ name: "inProgress", task: createDummyInProgressTask() },
		{ name: "done", task: createDummyDoneTask() },
	])("正常系: $name の Task は to したあと from すると元に戻る", ({ task }) => {
		// Given: ケースごとの状態に対応する Task を DTO に変換した値があるとき
		const item = toDynamoDBTaskItemDTO(task);

		// When: その DTO をドメインに変換すると
		const result = fromDynamoDBTaskItemDTO(item);

		// Then: 元の Task と一致する
		expect(result).toStrictEqual(task);
	});
});
```

### 保存キー

- [ ] 保存キーの生成関数が、仕様どおりの文字列を返す
- [ ] **ドメインが受け入れる最大の番号で、保存キーの連番が固定桁に収まる**
- [ ] 保存キーと本体が食い違う値を `from` が拒否し、issue の `path` がそのキーを指す（主キー・副次索引キーのそれぞれ）
- [ ] DTO スキーマが保存キーの形式（接頭辞・区切り・固定桁）を検査しているなら、その形式だけを破ったキーを `from` が拒否する（キーごと・形式の検査ごとに1ケース）
- [ ] 形式違反の識別子を持つ保存値を渡しても、`TypeError` のような意図しない例外ではなく `InvalidReconstructParamError` になる

**保存キーの形式を破ると、本体から導出した値との整合もたいてい同時に破れる。** 本体から導出したキーは必ず形式を満たすからである。
そのときは、形式の検査が出す issue（`code` と `path`）を確かめて、形式の検査が拒否したことを示す。種別だけでは、整合の検査が拒否した場合と区別できない
（実物は `example/infrastructure/dto/DynamoDBTaskItemDTO.test.ts` の「形式の issue」のテスト）。

**形式違反の識別子の観点は、どの検査が拒否したかではなく、保存キーの導出の途中で意図しない例外が出ないことを確かめる。**
区切りの無い識別子からは仕様どおりの保存キーを組めないので、キーとの整合も同時に破れてよい。テスト名と Then に「`TypeError` ではなく」と契約を書く。
ドメインの識別子の制約そのものは、ドメインのテストで確かめる。

**本体の項目を壊して `from` の拒否を確かめるときは、保存キーも壊した本体から組み直す。** キーを元のままにすると、キーと本体の整合の検査が先に拒否し、
ドメインの検査に届かない。拒否したのがどちらかは、捕まえたエラーの `operation` で確かめる（下の「DTO の形」の最後の項目）。
**保存キーのもとになる項目の型を壊すと（識別子を数値にするなど）、キーを組み直せない。** そのときは種別だけでなく、
型の検査が出す issue（`code` と `path`）を確かめて、型の検査が拒否したことを示す
（実物は `example/infrastructure/dto/DynamoDBTaskItemDTO.test.ts` の「id が数値」のテスト）。

### DTO の形

- [ ] **ドメインが受理する境界値で `to` → `from` が元の値と一致する**（表題の最大長、コレクションの最大件数、本文の最大長、タイムスタンプの上限、番号の最大桁、識別子の最大長）。保存形式が有効なドメイン値をすべて表現できることを確かめる
- [ ] 保存先に1件あたりの容量の上限があるなら、件数と文字数がすべて上限いっぱいで、1文字が最大のバイト数になる文字で埋めた値の保存形式が、その上限に収まる（`references/persistence.md` の「DTO スキーマの契約」）
- [ ] 必須キーの欠落を `from` が拒否する
- [ ] 型違い（数値の項目に文字列）を `from` が拒否する
- [ ] 余剰キーを `from` が拒否する
- [ ] 知らない判別子の値を `from` が拒否する
- [ ] **スプレッドで不変条件を破った完成値型の値を、`to` が `FatalUnreachableError` で拒否する**（ブランドは型の上の目印なので、`{ ...task, title: "" }` は型検査を通る。保存形式にする前の検査が効いていることを確かめる）
- [ ] **DTO は受理し、ドメインだけが拒否する代表の入力を、`from` が `InvalidReconstructParamError` で拒否する。** 1つの項目で決まる制約と、項目どうしの制約を、それぞれ1ケースずつ。拒否したのがドメインであることを、捕まえたエラーの `operation`（`"Task.reconstruct"`）で確かめる。種別だけでは DTO が拒否した場合と区別できない

DTO が落とすか `reconstruct` が落とすかの分担は、代表のケースで足りる。
細かい境界値はドメインのテストが持っているので、DTO で書き直さない。

## インフラ: リポジトリ実装

クライアントをモックに差し替えて確かめる（書き方は `references/test-style-mocks.md`）。
「送るコマンド」と「応答から組み立てた結果」は、別のテストにする。

- [ ] 1件取得が、仕様から書き下ろした保存キーとテーブル名でコマンドを送る
- [ ] 1件取得の応答に項目が無いとき、`undefined` を返す
- [ ] 1件取得の応答の DTO から、期待するドメインの値を組み立てる
- [ ] 応答の DTO が壊れているとき、`InvalidReconstructParamError` になる
- [ ] 一覧取得が、パーティションキー・件数・並び順の指定を持つコマンドを送る（並び順はインターフェースの JSDoc の約束と一致する）
- [ ] 一覧取得の応答に項目が無いとき、空の配列を返す
- [ ] 一覧取得が、応答の並びのままドメインの値を返す
- [ ] 応答が続きのキーを返したら、そのキーと残りの件数で続きを取り、取った順につなげて返す
- [ ] 指定した件数に達したら、続きのキーがあっても次の問い合わせを送らない
- [ ] 件数の引数が受け付ける範囲の外（負の数、小数、NaN）なら、問い合わせを送らずに名前の付いたエラーになる。受け付ける範囲の端（0件、1件）の扱いが JSDoc の約束どおり
- [ ] 保存が、書き下ろした DTO を持つコマンドを送る
- [ ] クライアントが失敗したとき、その失敗が呼び出し側に伝わる（握りつぶさない）

## インフラ: ドメインサービスの実装

クライアントをモックに差し替えて確かめる。

- [ ] 仕様どおりのキーと更新式でコマンドを送る
- [ ] 正常な応答から、期待するドメインの値を組み立てる（カウンタの値と組み立てた識別子を値で突き合わせる）
- [ ] ドメインが受け入れる最大の番号で成功する
- [ ] **保存先の応答が期待する型でないとき（`"1"`、`[1]`、項目の欠落）、何が起きたかを表す名前のエラーになる**
- [ ] 保存先の応答がドメインの受け入れ範囲を超えたとき（`0`、上限の1つ上）、同じ名前のエラーになる
- [ ] エラーが `operation` と、失敗した対象を特定できる値（採番なら `projectId`）を持つ
- [ ] クライアントが失敗したとき、その失敗が呼び出し側に伝わる

## 範囲外: 本物のクライアントで確かめる契約

本物のクライアントで実際の保存先に接続しないと確かめられない。このスキルではテストを書かず、統合テストの仕組みで確かめる。

- 保存した値を、同じ識別子で実際に取得できる
- 一覧取得が、実際の保存先でインターフェースに書いた順序で返る（ソートキーの並び）
- 条件式や更新式が、保存先で意図どおりに評価される
- 採番が原子的で、同時に採番しても同じ番号を返さない
