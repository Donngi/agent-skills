# DTO と永続化

保存先とやり取りする層（DTO・リポジトリ実装・ドメインサービス実装）の規則。
ドメインの規則ではないので、これらを書くときにここを読む。
実物は `example/infrastructure/` にある。

## 公開の形

**インフラ層は、必要なものを名前付きで export するだけにする。「公開 API」のオブジェクトを作らない。**
DTO の変換は `toXxxDTO` / `fromXxxDTO` / `toXxxDTOPKSK` / `toXxxDTOPK` を直接 export する。
インターフェースの実装は生成関数を `createXxxImpl` として export する。
エラーは class を名前付きで export する（共有の `shared-errors.ts` も、インターフェースのファイルに置いたものも）。

インフラ層でオブジェクトに集めない理由は2つある。

- **関数名がすでにモデル名を含んでいる。** `toDynamoDBTaskItemDTO` は、それだけでどの DTO への変換かが読める。
  オブジェクトに入れて `DynamoDBTaskItemDTO.to` と書いても、増える情報が無い
- **型と同名の値ができてしまう。** DTO の型は `DynamoDBTaskItemDTO`、公開オブジェクトも
  `DynamoDBTaskItemDTO` になり、`import { DynamoDBTaskItemDTO }` がどちらを指すか読み手に分からない

```ts
// ✗ インフラ層でオブジェクトに集めている。型 DynamoDBTaskItemDTO と名前が衝突する
export const DynamoDBTaskItemDTO = {
	key: toDynamoDBTaskItemDTOPKSK,
	to: toDynamoDBTaskItemDTO,
	from: fromDynamoDBTaskItemDTO,
} as const;

// ✓ 必要なものを名前付きで export する
export function toDynamoDBTaskItemDTOPKSK(id: TaskId): …
export function toDynamoDBTaskItemDTO(task: Task): DynamoDBTaskItemDTO
export function fromDynamoDBTaskItemDTO(raw: unknown): Task
```

**export するのは、ファイルの外から実際に使うものだけにする。**
DTO なら、変換の関数4つと、その戻り値の型である。

| 名前 | export | 理由 |
|---|---|---|
| `toXxxDTO` / `fromXxxDTO` | する | 呼び出し側が使う |
| `toXxxDTOPKSK` / `toXxxDTOPK` | する | リポジトリ実装がキーを組むのに使う |
| `XxxDTO`（型） | する | 公開する関数の戻り値型 |
| `XxxDTOSchema` | **しない** | 検証はこのファイルの中で完結する。外から `safeParse` を呼ばせない |
| `toPKSKFromRawId`（検証前の文字列を受ける版） | **しない** | 横断検証から呼ぶための内部の関数 |

スキーマを export しないのは、**呼び出し側が `from` を通さずに検証できてしまうのを避ける**ためである。
壊れた保存値を `InvalidReconstructParamError` に包むのは `from` の役割で、そこを迂回させない。
これらのファイルにモデル用の公開オブジェクトを作らない。

## DTO の組み立てと satisfies

**DTO には `XxxSchemaInput` を作らない。** DTO スキーマは `transform` も `brand` も持たないので、
`z.input` と `z.output` が同じ型になる。`to` が組み立てるリテラルは、戻り値型を `DynamoDBTaskItemDTO` と
注釈した関数の中で、状態ごとに `switch` で `return` して検査する（`references/model-code.md`「分岐の書き方」を参照）。
書き忘れの検出は戻り値の位置で効く。キー名の打ち間違いも、正しいキーの欠落としてそこで止まる。
止まらないのは、共通部を組み立てる中間の関数に余分なキーを足した場合だけである（実測）。
それは実行時に `strictObject` が落とす。

## 保存キー

**保存キーの組み立ては、キー文字列ごとに DTO のファイルに1箇所だけ置く。**
`to` も `Get` も `Query` も DTO の整合検証も、そこから取る。
`Query` がパーティションキーだけを要るなら、その生成関数も公開して完全なキーの生成から
呼ぶ。パーティションキーを取り出すために架空の識別子を組み立てない。
DTO を持たない補助アイテム（採番のカウンタなど）のキーは、そのアイテムを扱う実装の中に
閉じてよい。他のファイルから同じキーを作らないことが条件である。
リポジトリ実装がキー文字列を自分で書くと、桁数や接頭辞を変えたときに保存側だけが変わり、
読む側は永遠に `undefined` を受け取る。

**数値を固定桁の保存キーにするなら、受け入れる最大値を先に決める。**
`padStart` は指定桁を超えた文字列を短くしない。ドメインが受け入れる番号と採番が返す番号を、
保存キーがすべて表現できることを確かめる。

## DTO スキーマの契約

**DTO スキーマは保存形式の契約を定義する。ドメインの制約との一致を求めない。**
書くのは、必須キー、型、状態別の構造、余剰キーの拒否、保存上の列挙、
保存キーの形式と本体との整合である。長さ・形式・範囲・件数をドメインから写さない。
保存形式そのものに必要な条件だけを置く。業務の不変条件は、1つの項目で決まるものも
項目どうしの関係も、ドメインの完成値スキーマに置く。

判別子の `literal` と列挙の `enum` は値の制約ではなく型である。**`reconstruct` に渡す値、
つまり DTO の変換を終えたあとの値が `XxxSchemaInput` に代入できること。**
これが DTO の「形」の定義である。保存キーを除くだけで復元できる設計なら、DTO の出力型から
保存キーを除いたものがそのまま代入できる必要がある。参照実装の `priority` を `z.string()` に
すると、この受け渡しが型検査で止まる。保存側の判別子や列挙の表現がドメインと違うなら、
対応を変換の側に明示する。

**DTO の検証が通ったことを、ドメインとして制約を満たす値だとみなさない。**
`from` は `unknown` を DTO スキーマで検証し、項目の変換をしたあと、必ず `reconstruct` を
通して完成値を返す。業務上不正な値が DTO を通り抜けても、復元全体が失敗すればよい。
DTO に写しを置かなくても、`from` 全体では `reconstruct` が違反を拒否し、失敗の種別は
`InvalidReconstructParamError` になる。ただし DTO で先に失敗するとドメインの検証まで進まないので、
違反が複数あるときに返る issue の件数と `path` の一覧は同じにならない（実測）。
暗黙の補正で受理しない。

**いま書き込んでいる保存形式は、有効なドメイン値をすべて表現できなければならない。**
必要なのはこの包含であって、両者の制約の一致ではない。完成値から組み立てた保存値が
DTO スキーマを通ることを、全状態と境界値で確かめる。

**保存先に1件あたりの容量の上限があるなら、件数と文字数が上限いっぱいの値でも収まることを確かめる。**
DynamoDB の1項目は、属性名と値を合わせて 400KB までである。文字数の上限はコードポイントで数えるので、
1文字が UTF-8 で4バイトになる文字で埋めた場合がいちばん大きい。項目ごとの上限だけを見て通しても、
コレクションの件数と本文の長さを掛け合わせると収まらないことがある。そのときは保存が保存先のエラーで落ち、
ドメインでは有効な値を保存できない。収まらないなら、件数・文字数の上限を業務と決め直すか、保存形式を分ける
（子を別の項目にする、など）。上限の理由（保存先の容量）はドメインの JSDoc に書かず、
容量に収まることを DTO のテストで確かめる。参照実装はコメント50件・本文1000文字・表題200文字・URL 2048文字で
約21万バイトになり、上限の半分ほどに収まる（`example/infrastructure/dto/DynamoDBTaskItemDTO.test.ts`）。

**業務の上限の定数を、DTO のために export しない。**
保存キーの固定桁のように保存形式だけが必要とする定数は、インフラ層が自分で持ち、
組み立てと検証で共有する。ドメインの定数を変えたときに保存形式まで一緒に変わらないようにする。
値が偶然同じでも、変えてよいタイミングが違うなら別の定数である。
検証するのは値の一致ではなく、表現できることと既存データを読めることである。

**ドメインの制約の変更と、保存形式の変更を分けて扱う。**
旧い形式の値が DTO を通ることは、いまのドメインへ復元できることを意味しない。
旧いデータを読み続ける必要がある変更では、旧形式の読み取りと、必要な移行の変換と、
いまの `reconstruct` までを明示する。形式を見分ける必要が出たときに版数を導入する。
要件が無いのに版数を足さない。

**既存データを読めることが要件に明示されているなら、この指針の既定を理由に受理範囲を狭めない。**
識別子の受け入れる表記の限定、日時の範囲、DTO の `strictObject` も、旧コードが受理していた値を
拒否するなら狭める変更である。旧コードが受理していて新しいコードが拒否する値を洗い出し、
互換を保つ読み取りの経路を示す。両立できないなら、読めなくなる値と必要な仕様変更を回答に書き、
その部分を未確定として扱う。

## インフラ層での値の生成と変換

**インフラ層がドメインの値を作るときは、公開 API を通す。完成値スキーマを直接 `safeParse` しない。**
保存先から読んだ値を戻すときは `reconstruct`、保存先の値を材料に新しい値を作るとき（採番した番号から識別子を組み立てるなど）は `create` を使う。
後者は復元ではないので、`reconstruct` を使わない。
完成値スキーマを直接通すと、そのモデルの生成の経路が2本になり、`create` に足した検証が片方に効かなくなる。
DTO の `from` が `Task.reconstruct` を通すのと同じ理由である。
採番のように、検証済みの値から組み立てていて失敗しないと分かっている箇所も、公開 API を通して
`FatalUnreachableError` に包む（`example/infrastructure/domain-service-impl/TaskNumberIssuerImpl.ts` が実物）。
**この規則は層をまたいで値を作るときのものである。** ドメイン層の中で、検証済みの部品から
値を組み立てて完成値スキーマで確かめる箇所（業務操作の導出、接頭辞付き識別子の読み取り）は対象外で、
完成値スキーマを直接 `safeParse` してよい（`Task.complete` の `WorkPeriodSchema`、
`TaskId.projectId` の `ProjectIdSchema` が実物）。`create` / `reconstruct` を呼ばないのは、
生成の経路を増やさないためである。

**DTO の `to` は、保存形式にする前に、渡された値を完成値スキーマで確かめる。**
引数が `Task` 型でも、不変条件を満たすとは限らない。ブランドはスプレッドで引き継がれるので、
規約に反してドメインの外で `{ ...task, title: "" }` と書いた値も `Task` 型になる（`references/model-code.md`「入口を create と reconstruct に絞る」）。
そのまま書き込むと、以後その集約の読み出しがすべて `InvalidReconstructParamError` になり、壊れたデータが残る。
失敗は `FatalUnreachableError` に包む。到達するのは規約に反して作られた値が渡されたときだけで、実装の不具合だからである。
値を作らずに確かめるだけなので、上の「公開 API を通す」と `references/model-code.md` の「ドメイン層の外から完成値スキーマを直接呼ばない」の対象外とする
（`example/infrastructure/dto/DynamoDBTaskItemDTO.ts` の `toDynamoDBTaskItemDTO` が実物）。

**インフラ層はどちらの向きでも `safeParse` を使う。包むエラーだけを変換の向きで分ける。**
ドメイン → DTO（`to`）は入力が完成値なので、DTO スキーマを通らないのは実装の不具合である。
失敗は `FatalUnreachableError` に包む。DTO → ドメイン（`from`）は `unknown` を受ける境界なので、
失敗は `InvalidReconstructParamError` に包む。`reconstruct` の失敗と同じ
「保存されている値が壊れている」であり、呼び出し側の打つ手も同じだからである。

**保存の変換は `to` / `from` の2つの関数で書く。`z.codec` は使わない。**
`z.codec` の `encode` が受け取るのは `z.input` なので、モデルのブランドも各項目のブランドも
外れている。`TaskId` を要求する保存キーの生成関数に渡すには、識別子をスキーマで検証し直して
ブランドを取り戻す必要がある（型アサーションを使わずに書けるが、保存のためだけの再検証と、
そこで失敗したときの分岐が増える）。`to` は完成値をそのまま受けるのでブランドが残り、
再検証も分岐も要らない。
`from` が `reconstruct` を通るのに対し、codec は変換先のスキーマを内側で直接通すので、
復元の経路が2本になる。
呼び出し方も向きで変わる。復元は `codec.safeParse`、保存は `z.safeEncode` で、
`z.safeDecode` は `unknown` を受け取れない。`to` / `from` はどちらも `safeParse` の1つの形で書ける。
`references/pitfalls.md` の codec の節は、他所で見かけたときに読めるようにするためのもので、
この指針では使わない。

## リポジトリインターフェースの約束

### 同時更新

**集約の同時更新をどう扱うかは、要件として決める。** 同じ集約を2つの処理が読み、それぞれ変更して保存すると、
後から保存したほうが先の変更を黙って消す（コメントが1件消える、完了が着手中に戻る、など）。
**たいていは楽観ロックで足りる**（悲観ロックは要らない）。集約に版数を持たせ、保存を
「読んだときの版数と一致するときだけ書く」条件付きの書き込みにし、食い違ったら名前の付いたエラーを返す。
新規作成は「まだ無いときだけ書く」にして、既にある集約を黙って上書きしない。
要件に定めが無ければ、楽観ロックを提案して利用者に確認する。
参照実装の `TaskRepositoryImpl` はサンプルなので、この検出を省き、保存は置き換えるだけにしてある
（`TaskRepository.put` の JSDoc に「同時更新は検出しない」と書いてある）。写すときに省いたまま使わない。

**複数の集約にまたがる規則も、同時更新は楽観ロックでよいという要件のもとで扱う。**
「プロジェクトで同時に進行中にできるタスクは N 件まで」や「アーカイブ済みのプロジェクトにはタスクを作れない」は、
判定したあとに別の要求が同じ判定を通ったり、別の操作が判定の元の集約を変えたりする競合を、1つの集約の版数だけでは止められない。
一時的に上限を超える、確かめたあとにアーカイブされたプロジェクトにタスクができる、といったことを要件として許すかを決める。
厳密に守る必要があるなら、判定の元になる集約（プロジェクト）の版数を条件に保存するなど、保存先の条件付き書き込みで直列にする。
定めが無ければ、楽観ロックの範囲で許すことを提案して利用者に確認する。

### 順序・件数・不在

**インターフェースの JSDoc に書いた順序・件数の約束は、実装が保証できるものだけにする。**
数値の連番を文字列のソートキーに入れると、文字列比較で `10` が `9` より前に来る。
順序を約束するなら、桁を固定するか、別の属性で並べる。約束を書くより先に、
キー設計がそれを支えられるかを確かめる。

**一覧取得は、約束した件数に達するか終わりまで、保存先の続きを取り続ける。**
DynamoDB の `Query` は、`Limit` に達していなくても 1MB で結果を区切り、続きのキー（`LastEvaluatedKey`）を返す。
1回の問い合わせで返すと、データが増えたときに黙って件数が足りなくなる。続きのキーを `ExclusiveStartKey` に渡して取り続ける
（`example/infrastructure/repository-impl/TaskRepositoryImpl.ts` の `listByProject` が実物）。
呼び出し側にページを見せる契約にするなら、続きのキーをインターフェースに出し、JSDoc にそう書く。
**件数の引数は、受け付ける範囲を JSDoc に書き、問い合わせる前に確かめる。** DynamoDB の `Limit` は1以上の整数でなければならず、それ以外は保存先の検証エラーがそのまま上がる。
参照実装は、0 なら問い合わせずに空の配列を返し、負の数・小数・NaN は `ListLimitOutOfRangeError` にする。

**「無かった」はエラーにせず `undefined` を返す。** 1件取得のインターフェースは
`Promise<Xxx | undefined>` を返し、JSDoc に「無ければ undefined」と書く。
特別な事情が無いかぎりこれを既定にする。

無いことは多くの場合ただの分岐である。「無ければ作る」「無ければ空で表示する」と
書きたいだけの呼び出し側に、例外のための `try/catch` を書かせることになる。
迷ったら `undefined` にする。

エラーにしてよいのは、**無いこと自体が呼び出し側の誤りだと言い切れるとき**だけである。
その判断はモデルではなく、呼ぶ側の業務が持っている。判断が要るなら、
`undefined` を返してから呼び出し側で投げさせる。

## 外部応答

**外部応答の `unknown` を文字列に埋め込む前に、期待する型を検証する。**
組み立てたあとの文字列だけを検証しても、文字列化で消えた型の違いは見つからない。
採番結果なら、整数であることと採番できる範囲を確かめてから識別子を組み立てる。
