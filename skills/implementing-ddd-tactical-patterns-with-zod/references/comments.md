# コメントと語

JSDoc・`//` コメント・コメントやメッセージに使う語の規則。

## コメントの置き場

置き場によって届く先が違う。**仕様はスキーマのプロパティに JSDoc で書く。**

次は `example/domain/entity/Comment.ts` の `CommentFields` からの抜粋である。完成値スキーマと
create の第1引数スキーマは、このフィールド定義を共有する。全体は `example/domain/entity/Comment.ts` にある。

```ts
const CommentFields = {
	/** コメントの識別子 */
	id: CommentIdSchema,
	/** 著者 */
	authorId: UserIdSchema,
	/** 本文 */
	body: z
		.string()
		.min(1, { error: "コメントの本文は1文字以上です" })
		.max(1000, { error: "コメントの本文は1000文字までです" })
		.refine((v) => v === v.trim(), {
			error: "コメントの本文の前後に空白を含めることはできません",
		}),
	/** 投稿のタイムスタンプ */
	postedAt: TimestampSchema,
};
```

`z.strictObject` に渡すフィールド定義に書いた JSDoc は、`z.output` と `.brand()` と `.readonly()` と `z.discriminatedUnion` を通り抜けて、**推論された型のプロパティまで届く**。利用側で `comment.body` にホバーしても、`Task.create({ ... })` の引数を書いている最中にも同じ説明が出る。だから項目について書くことがあるなら、モデル全体のコメントではなくプロパティ側に書く。
**ただし書けるのは、コードから読み取れない利用上の仕様だけである。** スキーマに書いてある
制約（`min` / `max` / `regex` / `enum`）は書き写さない。

| 書く場所 | 届く先 | 何を書くか |
|---|---|---|
| スキーマのプロパティ | 利用側のホバー、補完 | その項目が何か。コードから読み取れない利用上の仕様（並び順・単位・境界の扱いを含む）と、業務の知識に由来する制約の理由。**上限や形式の書き写しと、設計の都合に由来する理由は書かない**（下の「理由を書くかどうか」） |
| ローカル関数 | 呼び出し箇所のホバー | **関数名から読み取れないことと `@throws`。** 名前の言い換えは書かない。`createXxx` / `reconstructXxx` / DTO の `fromXxx` にも書く。省いてよいのは `FatalUnreachableError` だけである |
| インターフェースのメソッド | 実装を知らない利用側のホバー | 実装が投げるドメインエラーを `@throws` で書く。利用側はインターフェースの型しか見ない |
| 型と完成値スキーマ | ホバー | そのモデルが何か。**構造の説明は書かない** |
| セクション内の `//` | 読んだ人だけ | Zod の落とし穴、その順序や配置でなければ壊れる理由、別の書き方を採らなかった理由、業務の知識 |
| `.meta({ description })` | 実行時と JSON Schema | 機械が読み出すときだけ |

ホバーに出るのは `/** */` だけ。`//` も `/* */`（アスタリスク1つ）も出ない。実測で確認した挙動なので、届けたい説明は必ず `/** */` で書く。

**JSDoc には利用側が知るべき仕様だけを書く。実装の都合は `//` でその行の隣に書く。** 利用側は実装コードを見ないので、`z.url()` の呼び出し順のような話を JSDoc に書いても文脈がなく意味が通らない。

```ts
/** http と https の URL */
const HttpUrlSchema = z
	.string()
	// z.url() は前後の空白を暗黙に除去し、途中の改行・タブ・CR も取り除く。
	// 後ろに置くと除去後の値しか見えないので、これらの拒否はここに置く
	.refine((v) => v === v.trim(), {
		error: "URL の前後に空白を含めることはできません",
	})
	.refine((v) => !/[\t\n\r]/.test(v), {
		error: "URL に改行やタブを含めることはできません",
	})
	.pipe(z.url({ protocol: /^https?$/ }));
```

**タグは `@throws` と、廃止予定を示す `@deprecated` の2つだけを使う。** `@throws` の書式は TSDoc の `@throws`（Extended のブロックタグ）に合わせ、例外の種類ごとに1ブロック書く。
`@param` `@returns` `@remarks` `@example` は使わない。パラメータと戻り値は型と名前で読め、
型で表せない利用条件はパラメータオブジェクトのプロパティの JSDoc か本文に書くほうが、同じ経路でホバーに届く。
JSDoc の中のコード例は型検査されないので、実装と食い違ったまま残る。
`@deprecated` は廃止予定を示すときにだけ書く（TypeScript の言語サービスが取り消し線で表示する）。
TSDoc は「このタグを書け」という規格ではなく、書いたタグをツールがどう解釈するかの取り決めである。
標準にあることを、タグを足す理由にしない。

`.meta()` は IDE のホバーには出ない。逆に JSDoc は実行時に読めない。説明文を読み出すコードが実際にあるときだけ `.meta()` を足す。無いなら JSDoc だけでよく、ビルドで消えるぶんバンドルにも載らない。

**制約はコードに書いてある。JSDoc に書き写さない。**

```ts
// ✗ min / max / regex を読めば分かる
/** 表題。1文字以上200文字以下。前後の空白は受け付けない。 */
title: z.string().min(1).max(200).refine((v) => v === v.trim()),

// ✓ 項目が何かだけ
/** 表題 */
title: z.string().min(1).max(200).refine((v) => v === v.trim()),

// ✓ 制約の「理由」はコードから読めないので書く
/** 見積りの大きさ。0は「見積っていない」と区別できないので受け付けない。 */
amount: z.int().positive(),
```

**例外は、利用者が値を使うときに頼る約束である。** 並び順（「投稿順に並ぶ」）、単位（「Unix epoch ミリ秒」）、
境界で同じ値を許すか（「着手と同じ値は許す」）は、スキーマに書いてあっても `refine` の中身を追ったり
`>=` と `>` を見比べたりしないと分からない。値を受け取った側がホバーで知りたい情報なので、書いてよい。
長さや件数の上限、形式（`regex`）、列挙の値は、スキーマを見ればそのまま読めるので書き写さない。
**列挙は、値を並べるのは書き写しだが、各値の業務上の意味を書くのはよい。** `/** 見積りの単位。point か hour。 */` は
`z.enum` を読めば分かる。`/** 見積りの単位。point はストーリーポイント、hour は人時。 */`（`example/domain/value-object/Estimate.ts`）のように、
値の名前だけでは分からない意味を書くのは、コードから読めないので書いてよい。

```ts
// ✓ 利用者が頼る約束。refine を追わないと並び順が分からない
/** 追加されたコメント。投稿順に並ぶ。 */
comments: z.array(CommentSchema).refine(/* 投稿順 */).readonly(),

// ✓ 境界で同じ値を許すかと、その業務上の理由
/** 完了のタイムスタンプ。着手と同じ値は許す（同一ミリ秒で終わることはありうる）。 */
completedAt: TimestampSchema,
```

**関数名の言い換えを書かない。**

```ts
// ✗ 関数名で分かる
/** 本文が変わっても同じコメントである。 */
function commentEqualsById(a: Comment, b: Comment): boolean;

// ✓ 書かない
function commentEqualsById(a: Comment, b: Comment): boolean;
```

### 理由を書くかどうか

**理由を書くかどうかは、その理由がどこから来たかで決める。**

| 理由の出どころ | 例 | 書くか |
|---|---|---|
| 業務の知識 | 「0は『見積っていない』と区別できないので受け付けない」「タスク番号は欠番を詰め直さない」 | 書く。コードから読めない |
| 設計の都合（この指針の規則、モデリングの選択） | 「別の集約なので識別子で参照する」「集約の内側なので値ごと持つ」「状態別ユニオンで表す」 | プロパティと型の JSDoc には書かない。構造とこの指針を見れば分かる |
| 実装の都合（Zod の落とし穴、順序の制約、採らなかった書き方） | 「`z.url()` は前後の空白を除去するので、拒否は手前に置く」 | その行の隣の `//` に書く。利用側には文脈が無い |

置き場は読む人で決まる。利用側が知るべき業務の理由は JSDoc、実装を読む人が知るべき理由は `//` に書く。
制約そのもの（「1以上」）はスキーマに書いてあるので、どちらにも書き写さない。

**例外を投げる関数には `@throws` を書く。呼び出し側が受け取りうるエラーを、`FatalUnreachableError` 以外すべて並べる。**
これは一般的な TSDoc の慣例に合わせている。`@throws` は、その関数を呼ぶと何が投げられうるかという関数の約束を書くもので、
関数の中のどこで投げたかは問わない。その関数自身が投げるものに加えて、中で呼んだ具体的な関数から伝わるもの
（業務操作が中で呼ぶ子エンティティの `create` の `InvalidCreationParamError` など）も書く。
種別が規約で固定されている `createXxx` / `reconstructXxx` / DTO の `fromXxx` も省かない。
呼び出し箇所のホバーに何が飛ぶかが出ることに価値がある。
**注入した依存（インターフェース）が投げるものは書かない。** 実装によって変わるので、インターフェースの側の `@throws` が担う。
**インターフェースの実装のメソッドにも同じ規則で書く。** 実装のメソッドは具体的な関数なので、自分で投げるものと、中で呼んだ具体的な関数
（DTO の `fromXxx` の `InvalidReconstructParamError` など）から伝わるものを並べる。多くはインターフェースの `@throws` と同じ並びになる。
実装の中で使うクライアント（SDK）が投げる例外は、包まずに伝えるので書かない。
分岐を足したり消したりしたら `@throws` も直す。
`FatalUnreachableError` は到達しない分岐を表し、呼び出し側に打つ手が無いので書かない。

**型や関数名から分からない利用条件は消さない。** 識別子の等価性を比べてよい範囲、
`number` で受け渡す日時の単位、採番が欠番を許すかどうかは、公開する操作か依存の型の
JSDoc に残す。別のファイルを読まないと分からない条件を、関数名の言い換えと同じ扱いで消さない。

**構造の説明を書かない。** 「判別可能ユニオンで表す」「集約の内側で識別子を持つ子エンティティ」は
どちらもコードと親のフィールドを見れば分かる。書くのはそのモデルが業務で何かだけである。

```ts
// ✗ スキーマを見れば分かる。後半はこの指針の規約でもある
/**
 * Priority
 * タスクの優先度。列挙なのでブランドを付けない。値そのものが型になる。
 */

/**
 * Project
 * タスクをまとめる単位。状態を1つしか持たないエンティティ。
 */

/**
 * TaskRepository
 * タスクの永続層への入出力インターフェース。保存先を知らない。実装はインフラ層に置く。
 * 引数と戻り値はドメインの型だけで表す。DTO も保存先の語彙もここには出さない。
 */

// ✓ 業務で何かだけを書く
/**
 * Priority
 * タスクの優先度。
 */
```

スキーマの途中に挟む行コメントも同じである。`refine` の位置が項目側かオブジェクト側かは、
書いてある場所を見れば分かる。

`//` の行コメントに書いてよいのは次の2つだけ。

1. **ドメイン知識** — 業務でそう決まっていること。なぜその値を保存するのか。
2. **コードを読むだけでは判断できない実装判断** — Zod の挙動の落とし穴、この順序でなければ壊れる理由、他の書き方を採らなかった理由（ドメインサービスにした理由のように、別の置き場を選ばなかった理由を含む）。

この指針の規則をなぞっただけの文（「別の集約なので識別子で参照する」）は、どちらにも当たらない。

**何が起きたかは能動で書く。** 「その操作を許さない状態のタスクに対して呼ばれた」ではなく
「その操作を許さない状態のタスクに対して処理を実行しようとした」と書く。受け身にすると、
誰が何をして失敗したのかが落ちる。

**「範囲」「上限」とだけ書かない。** 何の範囲で、何の上限かを書く。
「合計が扱える範囲を超えた」ではなく「合計が `Number.MAX_SAFE_INTEGER` を超えた」、
「上限を超えた」ではなく「件数が上限を超えた」と書く。
言語や実行環境が決めている境界なら、その定数名をそのまま書けば一意に決まる。

**同じ操作を別の動詞で呼ばない。** `to` を「写す」、`from` を「戻す」と書き分けると、
向きが違うだけの同じ変換に見えなくなる。どちらも「変換する」でよい。

**説明を書くなら、文として読める日本語にする。** 名詞句を切り詰めて意味を圧縮すると、
書いた本人にしか通じない。項目名の言い換えで足りるものは名詞のままでよく、句点も付けない。

```ts
// ✗ 名詞句に詰め込んでいて、何の位置なのか読み取れない
/** 高い順に並べたときの位置。保存はしない。 */

// ✓ 何に使う値で、どちらが大きいのかを書く
/** 並べ替えに使う序数。小さいほど優先度が高い。 */

// ✓ 項目名の言い換えで足りるなら名詞のまま。句点は付けない
/** 担当者 */
```

**`//` のコメントは、最後の行にだけ句点を付けない。** 途中の文は `。` で区切り、
末尾は句点なしで止める。JSDoc は `/** 〜。 */` のように句点で閉じる。
形が決まっていれば、どこで文が終わっているかを読む側が数えずに済む。

```ts
// ✗ 末尾にも句点がある
// z.uuid() は大文字を通す。表記が揺れると同じ識別子が2つ共存する。

// ✓ 途中は句点で区切り、末尾は付けない
// z.uuid() は大文字を通す。表記が揺れると同じ識別子が2つ共存する
```

**「〜すれば足りる」「〜で十分」のように読み手に補わせない。** 何をどう判定しているのかを
言い切る。「同じ位置どうしを比べれば足りる」ではなく
「同インデックスの同値性で判定できる」と書く。

**規約に従ったことを報告するだけのコメントは書かない。** 「公開 API はオブジェクトに集める」「共通フィールドは切り出さない」「create の第1引数の型は z.output から取る」のように、何をしたかだけを述べる文は読む人の役に立たない。
テストの `// Given:` `// When:` `// Then:` `// And:` とその説明は、テストの構造と各セクションで何をしているかを示すもので、この規則の対象外である。
コードを読めば分かることでも書く（理由と書き方は `references/test-style.md`）。説明がコードと食い違っていないことは完了の確認で確かめる。

**その場所に効くライブラリの挙動、破ったときに壊れる仕組み、その配置や順序にした理由は書いてよい。** この指針に同じことが書いてある、という理由だけでは消さない。コードを読む人は指針を開いていない。

判断に迷ったら、**「このコメントは、この行のコードについての説明か」**を問う。どのコードの隣に置いても同じように読める文なら、規約の報告である。この行を変えたら嘘になる文なら、その場所のコメントである。

**写したコメントは、写した先のコードと照らし合わせる。** 参照実装のコメントを、検査の数や順序が違う場所に持ち込むと、実装と食い違った説明が残る。規約の言い直しより読む人を誤らせる。

```ts
// ✗ 規約の言い直し。読む人の役に立たない
// 操作はモデル名のオブジェクトに集めて公開する
export const Task = { /* ... */ } as const;

// ✗ 中核の規則をそのまま写している。スキーマを見れば分かる
// ドメインでは正規化しない。整形済みの値だけを受け入れる
.refine((v) => v === v.trim(), {
	error: "表題の前後に空白を含めることはできません",
})

// ✗ 規約を写しただけ。破ると何が壊れるのかが書いていない
// ここで例外を投げる関数を呼ばない
.superRefine((v, ctx) => { /* ... */ })

// ✗ 事実だけで、何をしてはいけないのかが書いていない
// safeParse は例外を捕まえない
.superRefine((v, ctx) => { /* ... */ })

// ✓ してはいけないことと、破ったときに壊れるものを両方書く
// この中から例外を投げる関数を呼ばない。safeParse は例外を捕まえないので、
// safeParse を呼んだ場所すべてで意図しない例外になる
.superRefine((v, ctx) => { /* ... */ })

// ✗ 「そうしなかった」ことの報告。コードを見れば分かる
/**
 * UserProfile
 * 状態別ユニオンを持たないので、共通フィールドの部品は切り出さない。
 */

// ✗ モデリングの理由をプロパティの JSDoc に書いている
/** 責任者。別の集約なので識別子で参照する。 */
leadId: UserIdSchema,
/** 付いたコメント。集約の内側なので値ごと持つ。投稿順に並ぶ。 */
comments: z.array(CommentSchema).readonly(),

// ✓ プロパティには利用側が知るべき仕様だけを書く
/** 責任者 */
leadId: UserIdSchema,
/** 追加されたコメント。投稿順に並ぶ。 */
comments: z.array(CommentSchema).readonly(),

// ✓ 知らないと踏む挙動
// z.url() は前後の空白を暗黙に除去し、途中の改行・タブ・CR も取り除く。
// 後ろに refine を置いても、見えるのは除去後の値なので拒否できない

// ✓ ドメイン知識
// タスク番号はプロジェクトごとの連番。欠番が出ても詰め直さない
```

**この指針の書き方をした、という報告は書かない。** 「〜なので切り出さない」「〜なので入れない」の形の文は、ほぼ規約の言い直しになる。

**依頼文の言い直しも書かない。** 「コメントを子エンティティとして内包する」のような、頼まれた内容をそのまま繰り返す文は情報を足していない。

コードを読めば分かる自明なことは書かない。

## 語の選び方

コメント・テストの説明・エラーメッセージに書く語の規則。

**モデルに日本語名は無い。英名が正である。** `Task` は「タスク」ではなく `Task`、
`Estimate` は「見積り」ではなく `Estimate`、`Labels` は「ラベル集合」ではなく `Labels` と書く。
テストのコメントとテスト名、この指針が示すテストの例で、同じにする。
実装の JSDoc と、モデルの題材を説明する地の文は対象にしていない。
訳すと、同じモデルが「ラベル集合」と「ラベルの並び」のように複数の呼び名を持ち、
どれが正しいかを決める根拠が無くなる。英名なら、名前をコードが決めるので揺れない。

**項目名・状態名・依存は、日本語で書いてよい。** `startedAt` を「着手時刻」、`done` を「完了した」、
`clock` を「クロック」、`idGenerator` を「IDジェネレーター」と書く。
これらは役割を説明する語で、訳すと読み手の得る情報が増える。`Task` を「タスク」と書いても増えない。
ただし**その項目や定数そのものを確かめる箇所**（型のテスト、定数を直接渡す境界値のテスト）は識別子で書く。
`Number.MAX_SAFE_INTEGER` を「安全な整数の上限」とは書かない。

**同じ語がモデルと項目の両方を指しうるときは、その文が何を指しているかで決める。** 値オブジェクトは、それを持つモデルの項目にもなる
（`Task` の `id` 項目の型が `TaskId`）。文がモデルそのもの（生成する・復元する・等しいと判定される）を指すなら英名で書き、
持ち主のモデルの項目として述べるなら日本語でよい。

| 文 | 指しているもの | 書き方 |
|---|---|---|
| その文字列と同じ `TaskId` が返される | `TaskId.create` が返すモデル | 英名。「タスク ID が返される」とは書かない |
| 接頭辞が2文字の `ProjectId` の入力があるとき | `ProjectId.create` に渡すモデルの入力 | 英名 |
| 識別子が大文字を含む `Comment` の保存値で | `Comment` の `id` 項目（型は `CommentId`） | 項目なので「識別子」でよい |
| 作成時刻が負の保存値で | `createdAt` 項目（型は `Timestamp`） | 項目なので日本語でよい |
| その `ProjectId` に接頭辞を付けたキーになる | Given で渡した `ProjectId` そのもの（保存キーを組む関数の引数） | 英名。「そのプロジェクトコード」と言い換えない |

**Given で英名で書いたモデルを、When や Then で「その」で指し直すときも英名のまま書く。** `// Given: ProjectId があるとき` を受けた Then で
「そのプロジェクトコード」と書くと、同じ値に2つの呼び名が付く。DTO や保存キーの関数に値オブジェクトを1つ渡すテストで起きやすい。

語の出現だけで違反かどうかを決めない。定着した訳語が無い英単語を片仮名で書くのは訳ではない（`clock` の「クロック」）が、
モデル名には当てはめない（`Task` を「タスク」と書くのは、片仮名でもモデル名の訳である）。

**コード中の語も、エンジニアがそう呼ぶ形のまま書く。** `clock` は「時計」ではない。
`codec`、`payload` のような語も無理に訳さない。定着した訳語が無いなら、カタカナで書くほうが通じる。
操作名も言い換えない。`archive` は「アーカイブする」であって「閉じる」ではない。
言い換えると、コメントがどの識別子の話をしているのか追えなくなり、検索でも見つからなくなる。

定着した訳語があるものは訳してよい。`Id` 項目を「識別子」、`Title` 項目を「表題」と書くのは通じる
（モデル名の `TaskId` は `TaskId` と書く。項目の `id` の話とは別である）。
**`Id` は JSDoc では「識別子」、利用者が読むエラーメッセージでは「ID」に寄せる。** 混ぜない。
**エラーメッセージの「ID」には、どのモデルの ID かを付ける。** `ID は小文字です` ではなく
`コメント ID は小文字です` と書く。issue だけを見た人には、どの項目が落ちたのかが読めない。
遠回しな言い換えを避けるという話であって、すべてをカタカナにするという話ではない。

**日本語と英字の間には半角空白を入れる。** `不正な DTO で`、`その URL を持つ Task になる`。
句読点・括弧の直後と直前には入れない。`IDジェネレーター` のように語彙として固定した複合語は例外とする。
