# eval ケース一覧（26件）

設計の理由は `README.md` を参照。ここは何を測るかの一覧である。

題材は生成が図書館（蔵書・貸出・利用者）、レビューと修正が倉庫の在庫。
`files` に渡す既存コードは `fixtures/` にある。中身と使い分けは `fixtures/README.md` を参照。
「図書館の部品一式」は `fixtures/library/` に1つだけ置き、12〜15番で共有する。
25番だけ別の題材（延滞請求）を `fixtures/library-charge/` に持つ。導出値の実物が参照実装に無いためである。
1〜11番と16・17番と20番は `files` が空で、部品から書かせる。
`evals.src.json` の `files` はこのディレクトリからの相対パスで、`build.py` が `evals.json` ではスキルのルートからの相対パス（`evals/fixtures/...`）に直す。skill-creator の `files` の規約に合わせるためである。

レビューケースの期待違反とおとりは `expected-violations/` にある。**モデルには渡さない。**
25番の採点用の誤実装は `grading-aids/` にある。こちらも**モデルには渡さない。**

`基` は基準ケース（写しで通ってよい。回帰検出用）、`識` は識別ケース。合否の基準はどちらも同じで、スキルありで全採点項目が通ること（`RUNNING.md`）。

## 測っていないもの

次は、このスキルが扱うと決めた範囲にありながら、この eval では測っていない。
**通過率からこれらの能力を読み取らないこと。**

- **13・14番の C1（分岐網羅）**。カバレッジの採点は、対象ファイルが fixture で固定されている25番だけに配っている。
  13・14番は契約ごとのテストの有無を固有の観測で見るにとどめる
- **利用者に確認して答えをもらったあとの振る舞い**。18・19番は、既存の規約と `test-style.md` の既定が
  ぶつかる項目を挙げ、非対話の実行として既存の規約を優先して書くところまでを測る。答えを受けて書き直す経路を
  測るには複数ターンのケースが要る（`build.py` は単一の依頼文しか生成しない）
- **Jest / node:test / in-source testing の成功経路**。19番の fixture は Vitest の上で流儀だけが違う。
  別のライブラリへ読み替えた先を測るには、そのライブラリの fixture と依存が要る

## 共通プロファイル

プロファイルの一覧と配布先は `README.md`「プロファイルの assertion」の表だけが正である（`build.py` が各ケースの `inherits` と突き合わせる）。ここには除外の理由と、見落としやすい規則だけを書く。

`inherits` で配ったもののうち、そのケースで空虚に真になるもの、および
ケース固有の観測と同じ欠落を数えるものは、`excludes` に規則 ID を並べて落とす。
`build.py` が、継承側に無い ID を `excludes` に書いていればエラーで止める。
同じ ID が2つ入っていてもエラーで止める。

| ケース | 外すもの | 理由 |
|---|---|---|
| 1 | `no-transform` | 入力を書き換える段を繋がないことは、ケース固有の行（`toLowerCase` や `trim` を繋いでいない）で1回だけ数える |
| 2 | `no-transform` | 正規化せずに拒否することは、ケース固有の行（前後に空白を付けた入力が拒否される）で1回だけ数える |
| 3 | `refine-each-rejected` | 列挙だけで、`refine` も横断検証も無い。制約は `z.enum` の定義そのもので、拒否は固有の行（4区分の定義）と完成値スキーマの検証のテストで見る |
| 5 | `error-specific-name` | 包括的な名前を避けることは、失敗ごとに何が起きたかを表す名前を求めるケース固有の行で1回だけ数える（単位の不一致と桁あふれ） |
| 7 | `error-specific-name` | 包括的な名前を避けることは、失敗ごとに何が起きたかを表す名前を求めるケース固有の行で1回だけ数える（上限の超過） |
| 11 | `error-specific-name` | 包括的な名前を避けることは、失敗ごとに何が起きたかを表す名前を求めるケース固有の行で1回だけ数える（合計が計算できない） |
| 12 | `dto-shape` `no-domain-const` `key-one-place` `dto-enum` `reconstruct-minimal` | 同じ欠落をケース固有の観測が数えている。`reconstruct-minimal` は DTO に `reconstruct` が無い |
| 13 | `throws` `reconstruct-minimal` `refine-each-rejected` | 実装の各メソッドに DTO の `from` から伝わるものを `@throws` で書くことは、ケース固有の行で1回だけ数える（`references/comments.md` の「インターフェースの実装のメソッドにも同じ規則で書く」）。`reconstruct` もスキーマも持たない |

`all` に入れるもののうち、見落としやすいもの。

- 依頼にない項目・状態・不変条件・数値を足さない（図書館は貸出上限・延滞料金・予約待ちを発明しやすい）。依頼に無い件数・文字数の上限は、暫定と明示しても置かない（`[no-provisional-limit]`）
- 規約に従ったことを報告するだけのコメント（`[no-echo-comment]`）と、置いた場所の実装と食い違うコメント（`[comment-accurate]`）を別の行で見る。回答の地の文が受け入れる値・拒否する値・振る舞いを実装と食い違って説明していないか（`[answer-accurate]`）も別の行で見る
- コード中の語を訳さない（`clock` を「時計」と書かない）
- `.meta()` を読み出しコードが無いのに足さない
- テストは存在確認ではなく、誤実装を落とせるかで見る

`model` に入れるもの。

- 公開面の広さ（`[no-extra-api]`）。依頼に無い操作を何個公開しても `[no-invention]` の1件にしかならなかったので、公開する関数の範囲を別の行で見る。依頼か fixture から公開の必要が読み取れる読み取り関数は許す

`brand` に入れるもの。

- ブランドが出力側だけ（`inout` でない）
- ブランドを付けるべき完成値に付けている（`[brand-present]`）。`[brand-symbol]` は `.brand()` が1つも無ければ満たしたものになるので、付け忘れはこの行で数える
