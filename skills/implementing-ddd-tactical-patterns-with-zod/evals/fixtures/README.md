## 守っていること

- **題材を参照実装から外している。** 生成は図書館、レビューと修正は倉庫。
  `example/` のタスク管理とは語彙が重ならない
- **`tsc` が通る。** `--strict` と `exactOptionalPropertyTypes` を有効にして確認した
  （`example/tsconfig.json` と同じ設定）。
  違反を仕込んだ fixture も型検査は通る。レビューが型エラーの指摘に流れないようにするため
- **実行して挙動を確かめた。** 正しい fixture は往復し、違反を仕込んだ fixture は
  `../expected-violations/` に書いた壊れ方を実際に起こす（`warehouse/infrastructure-under-review` の
  codec は往復が壊れ、`warehouse/legacy` は読めるが保存が落ちる）
- **テストを仕込んだ fixture は緑で通す。** `warehouse/reviewed-tests` の9件の違反は、
  どれもテストを落とさない。落ちるテストを置くと、レビューが実行結果の指摘に流れて、
  「緑のまま誤実装を見逃す形」を読めるかを測れなくなる
- **AWS SDK に依存しない。** リポジトリ実装は SDK と同じ名前・同じ呼び出し方のスタブを
  ファイル内に置いている。`example/` と同じ書き方である
- **`shelf-app/biome.json` は入れ子の設定（`"root": false`）である。**
  このリポジトリの formatter が fixture の流儀を書き換えないようにするためでもある
- **テストは 19番と26番の fixture にだけ置いている。** 12〜14・22〜24 の fixture にテストを添えると、
  assertion が求めている「どこまで確かめるテストを書けるか」の答えを渡すことになる。
  19番は逆に「既存のテストの流儀に合わせられるか」を測るので、2本同梱する（`describe` を使わない書き方などが、
  1ファイルだけの特徴ではなくプロジェクトの流儀だと読めるようにするため。スキルは既存のテストが1つだけなら、その特徴を規則とみなさない）。
  **`references/testing.md` の必須ケースは fixture の評価対象ではない。**
  fixture は既存コードの抜粋として渡すもので、その網羅は受験者の出力で測る。
  19番に同梱した2本も、流儀を示すためのものであって必須ケースの網羅ではない

## 19番の fixture について

`shelf-app/` は次の点でこの指針と違う。合わせるべき既存の流儀として渡す。

| 項目 | このリポジトリ | `shelf-app/` |
|---|---|---|
| 字下げ・引用符・セミコロン | タブ・`"`・常に付ける | 空白2つ・`'`・省く |
| 末尾のカンマ | 付ける | 付けない（`trailingCommas: "none"`） |
| 行の幅 | 80 | 100 |
| フォルダ | `domain/value-object/` | `src/models/` |
| エラー定義の場所 | `domain/shared-errors.ts`（共有の分）と、各モデルのファイルのエラーのセクション | `src/errors.ts`（全部を1つのファイル） |
| セクションの区切り | `// ---- 名前 ----`（37桁の罫線） | `// ===== 名前 =====` |
| セクションの名前 | スキーマ・型定義 / ファクトリー関数 / 再生成関数 | スキーマ / 生成 / 復元 |
| 公開の形 | モデル名のオブジェクト | 関数ごとに名前付き export |
| テストの置き場と書き方 | 対象の横の `Xxx.test.ts`・`describe` は公開 API のキー単位・`test` | `__tests__/*.spec.ts`・`describe` を使わず `test` だけ |

`biome.json` の `$schema` は 2.3.7 を指している。CLI（2.5.1）との差で `biome check` が info を1件出すが、整形結果は変わらない。
整形を確かめる biome は 2.5.1 を使う（実行役の作業場所に置く `node_modules` にも入れる。`RUNNING.md`「実行役に渡すもの」）。

**`"root": false` は、このリポジトリの formatter が fixture の流儀を書き換えないために入れてある**（リポジトリの直下に biome の設定を置いたときに、入れ子の設定として扱われるようにする）。
入れ子の設定は上にルートの設定があって初めて効くので、fixture を単独で複製した場所では、複製側を `root: true` にしないと fixture の書式が使われない。**実行役に渡す複製も `true` にする**（`RUNNING.md`「実行役に渡すもの」）。
採点役がこの設定で整形を検証するときは、`--config-path` が `root: false` の設定を拒否するので、
fixture ごと作業ディレクトリに複製して、複製側の `biome.json` の `root` を `true` に書き換えてから
`npx biome format` を掛ける。fixture 本体の設定は変えない。
出力の書式を比べるだけなら、`iteration-N` の成果物を同じように複製して掛ければよい。

## 「正しい見本」の fixture が守っていること

`library/`・`library-charge/`・`warehouse/domain/`・`warehouse/infrastructure/` は、現行の規則どおりに書いてある。
受験者はこれを既存コードとして読み、形を真似る。**規則に遅れた箇所が残ると、真似た出力が共通の行で落ち、
基準ケースの通過率が原理的に100%にならない。** レビューケースで同じ形を違反として数えていれば、矛盾にもなる
（以前は、エラーが対象の識別子を持たない、作成用スキーマに `.readonly()` が無い、保存キーの関数が
「スキーマ・型定義」のセクションにある、の3つがこれに当たっていた）。
とくに次を守っている。規則を変えたら、ここと fixture を一緒に直す。

- 業務のエラーが対象の識別子を持ち、識別子・日時・状態をドメインの型のまま持つ（生の `string` / `number` に落とさない）
- 作成用のスキーマに `.readonly()` が付いている
- DTO の保存キーの関数が「変換」のセクションにある
- DTO の `to` が、保存形式に組み立てる前に完成値スキーマで値を確かめる
- `reconstruct` を呼ぶのは DTO の `from` だけ
- メッセージが「〜です」「〜できません」で言い切ってある
- モデルのファイルの「エラー」のセクションが「公開 API」の1つ上にある
- インターフェースの実装のメソッドに、DTO の `from` から伝わる `InvalidReconstructParamError` の `@throws` がある

## 意図的に残した逸脱

「正しい見本」の中で、規則の既定から外れている箇所。**これ以外の逸脱は直す。**

| 場所 | 逸脱 | 残す理由 |
|---|---|---|
| `warehouse/domain/entity/StockItem.ts` の `QUANTITY_MAX` | 業務の定数を、ドメインの外が要らないのに export している | 下の節のとおり、22番の期待違反 I2 を成立させるため |
| 各 `repository/` のインターフェースの `put` | 集約を無条件に上書きし、同時更新の競合を検出しない | 同時更新は楽観ロックで検出すれば足りる（要件）が、参照実装の `TaskRepository.put` と同じく、サンプルなので検出を省いている（`references/persistence.md` の「同時更新」） |

## `warehouse/domain/` の `QUANTITY_MAX` について

この定数を `export` しているのは、ケース22の期待違反 I2（DTO がドメインの上限定数を
import している）を成立させるためである。ドメインの中では宣言したファイルでしか使わない。
ケース24でこのファイルを直すときに「使われていない export」として消さないこと。
