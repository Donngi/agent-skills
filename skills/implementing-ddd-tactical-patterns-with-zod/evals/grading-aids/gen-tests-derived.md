# 25番 gen-tests-derived の採点用の誤実装

**モデルには渡さない。** `expected-violations/` と同じ扱いである。

提出されたテストが「誤実装を落とせるか」を、形の判定ではなく**実測**で見るための道具である。
自由生成のケースでは採点役が即興で誤実装を作ることになって安定しないので、
fixture が固定されているこのケースだけで使う。

## 手順

1. 作業用の場所（run のディレクトリの外。`RUNNING.md` を参照）に、渡した fixture と提出された成果物を複製する。
   `outputs/` そのものは変えない
2. まず複製をそのまま実行し、**提出されたテストが全部通ること**を確かめる。
   ここで落ちるなら、M1〜M3 の採点項目はどれも failed にし、evidence にその旨を書く
3. 誤実装を1つずつ当てて実行し、**狙った契約の assertion が落ちるか**を見る
4. 誤実装ごとの採点項目の evidence に、落ちたテストの名前と落ち方（assertion の失敗か、import・収集・ヘルパーの初期化の失敗か）を書く

## 検出成功の条件

**元の実装では通り、型検査を通る誤実装で、狙った契約の assertion が落ちること。**

import の失敗・テストの収集の失敗・ヘルパーの初期化の失敗は、検出成功に**数えない**。
これらは誤実装の中身と関係なく落ちるので、テストの検出力を示さない。

## M1: 明細の追加で割引額を0に戻してから請求額を求め直す

`domain/entity/OverdueCharge.ts` の `addOverdueChargeLine`（明細を追加する操作）で、
組み立てる値の `discountAmount` を `0` にし、`chargeAmount` を明細の合計そのものにする。

```ts
// 変更前: discountAmount は元の値のまま、chargeAmount = total - charge.discountAmount
// 変更後: discountAmount: 0, chargeAmount: total
```

**狙う契約**: 明細を追加したあと、割引額を変えずに請求額だけが求め直される。
提出されたテストに「割引額が0でない請求に明細を追加し、結果の請求額か割引額を、独立に組んだ期待値と比べる」
テストがあれば落ちる。

この誤実装は、請求額と明細の合計と割引額の関係を保つので、完成値スキーマの横断検証を通る。
**例外は出ないので、落ちるのは assertion だけである。** 横断検証に引っかかる誤実装（請求額を求め直さない、など）は
`FatalUnreachableError` が漏れて、請求額を見ないテストでも落ちるので、検出力を測れない。
割引額が0の請求だけで確かめるテストは、この誤実装を落とせない。それも検出失敗として記録する。

## M2: 横断検証から請求額の整合の検査を外す

完成値スキーマの `superRefine` から、「請求額 = 明細の合計 − 割引額」を確かめる分岐を落とす。
ほかの検査（金額の範囲など）は残す。

**狙う契約**: 再計算を忘れた保存値を `reconstruct` が拒否する。
提出されたテストに「請求額だけが食い違う保存値を `reconstruct` に渡すと拒否される」テストがあれば落ちる。

## M3: to で明細の金額と割引額を取り違える

`infrastructure/dto/DynamoDBOverdueChargeItemDTO.ts` の `to` で、
保存する明細の金額と割引額を入れ替える。`from` は変えない。

**狙う契約**: DTO の期待値を、独立に書いた保存表現と突き合わせている。
`from` は変えないので、往復のテストでも落ちる（実測: `from(to(charge))` が`InvalidReconstructParamError` になる）。
**落ちたテストの名前を必ず記録し、往復のテストで落ちたのか、独立対応のテストで落ちたのかを区別する。**
独立対応のテストで落ちて初めて、期待値を独立に書いていることの証拠になる。
