# eval の保守ガイド

`implementing-ddd-tactical-patterns-with-zod` スキルの eval を保守するための文書である。
テストケースを足す・直す・減らすとき、SKILL.md を変えて eval を追随させるときに読む。

前半は「なぜこの形なのか」（設計の前提）、後半は「どう直すか」（手順と書き方）である。
**手を動かす前に、変えようとしている箇所の前提をこの文書で確かめる。** 前提を知らずに
直すと、誤判定を生む書き方が戻ってくる。

# 設計の前提

## 何を測るのか

このスキルの eval が測るのは **規則を守って書けるか** である。
**測っていないものは `CASES.md`「測っていないもの」に挙げてある。**
13・14番の C1、`Result` への読み替えを承認したあとの実装、Jest / node:test / in-source の成功経路は、
通過率から読み取れない。
規則を暗唱できるかではない。だから「`@throws` の網羅だけを問う」ような
ケースは作らない。このスキルの eval は必ず何かのモデルを書かせることになるので、
そういう項目の実体は「どのケースにも掛かる assertion」か
「特定の依頼文で初めて発火する罠」のどちらかにしかならない。

## 4つのタスク種別

| 接頭辞 | 種別（`category`） | 何を測るか |
|---|---|---|
| `gen-` | 生成（`generation`） | 各パターンを規則どおりに書けるか |
| `trap-` | 生成・誘惑（`trap`） | 依頼文が違反を誘うとき、規則を優先できるか |
| `review-` | レビュー（`review`） | 規則違反を見つけ、正しいものを誤って指摘しないか |
| `fix-` | 修正（`fix`） | 既存コードを壊さずに規則へ寄せられるか |

**`trap-` を分けた理由。** 網羅ケースでは「たまたま守れた」のと
「規則を理解して守った」のを区別できない規則がある。
正規化しない、非同期の検証を入れない、依頼にない項目を足さない、
既存プロジェクトの規約に従う、といった規則がそれに当たる。
違反したくなる依頼文を与えて初めて差が出る。

**`review-` を別の種別にした理由。** 与えられたコードに規則を当てる能力と、
書くときに規則を守る能力は別である。前者ができても後者ができないことは普通にある。
レビューを「規則を守れるか」の代理指標にしない。
合否の基準は生成と同じで、スキルありで全採点項目が通ることである（下の「合否の出し方」）。
レビューの採点項目は、期待違反ごとの検出と、おとりや一覧に無い誤った指摘をしていないことを1行ずつ見る
（下の「レビューケースの採点」）。

**`fix-` は生成の勘定に入れる。** 最終的にコードを書かせるので、
測っているものは生成と同じである。既存コードという制約が付くぶん難度が高い。

## 題材を参照実装から外している理由

スキルは、コードを書く前に `example/` の該当する実物を読ませる。
題材が参照実装と同じだと、スキルを読んだモデルは正解を写すだけで満点が取れる。
測っているのが規則の適用ではなく検索になる。

**旧 `evals.json` は実際に漏れていた。** id=2 の依頼文は
「タスクの ID の値オブジェクト。`PROJ-123` のように」で、`TaskId.ts` そのものだった。

そこで題材を差し替えた。**構造は同じにする。** 同じでなければパターンを測れない。
変えるのは業務の題材だけである。

- 生成は図書館（蔵書・貸出・利用者）に寄せる。`files` を使い回せる
- レビューと修正は倉庫の在庫にする。fixture が生成側と混ざらない
- **参照実装の語彙（タスク・プロジェクト・コメント・ラベル・見積り）を依頼文にも fixture にも使わない**

`gen-errors` だけはエラー class（共有の `shared-errors.ts` と、貸出のエンティティのファイルのエラー）を書かせるので題材を変えようがない。
既定の2つ以外に足すエラーの名前だけを別題材から採る。

## 基準ケースと識別ケース

題材を変えても、名前を置き換えれば構造がそのまま一致するケースは残る。
**これは欠陥ではない。** このスキルは「該当パターンの実装例を読んでから書け」と
指示しているので、写して正しく出ることは意図した挙動である。

そこでケースの性格を2つに分けて、`CASES.md` と `evals.src.json` の `discriminative` に記録する
（`evals.json` には出さない。合否の基準はどちらも同じで、スキルありで通過率100%である）。

- **基準ケース**（`discriminative: false`）。`SKILL.md` や `example/` を変えたときに落ちる箇所を見るための回帰検出。
  対照との差が小さくても問題にしない
- **識別ケース**（`discriminative: true`）。規則を理解して未知の条件に適用できるかを見る

**落ちたときに疑う対象が違う。** 基準ケースがスキルありで落ちたら、まず assertion か依頼文の
不備を疑い、それが無ければ参照実装か規則の記述を直す。識別ケースが落ちたら規則そのものの
伝わり方を疑う。

識別力を上げたいときは、ケースを増やさず、**参照実装をそのまま使うと落ちる
業務条件を1ケースに1つだけ混ぜる。** 全部に混ぜると基準ケースとしての価値が消える。
1ケースに罠を2つ入れると、どちらで落ちたか読めなくなる。

## assertion の3層

旧 `evals.json` は共通の文言を11ケースにコピーしていた。
その結果、規則を変えたときに追随できず、**現行の規則が禁じていることを
「満たすべき」として書いた assertion が残っていた。**
DTO の制約をドメインと揃えることを要求する assertion が、
規則を逆転させたあとも残っていたのがその例である。

同じことを繰り返さないために3層にする。

1. **規則 ID。** 意味ベースの ID に、1つの要求と適用条件を持たせる。
   `evals.src.json` のプロファイルが規則辞書を兼ねる
2. **対象別プロファイル。** 規則をモデルの種類ごとに束ねたもの。ケースは `inherits` で選ぶ
3. **ケース固有の観測。** 「この題材で何を観測すれば判定できるか」を書く。
   規則の言い換えにしない

**旧ファイルから assertion を機械的に引き継がない。**

**規則の ID は意味ベースにする。** `SKILL.md` の規則番号や
完了チェックリストの通し番号を ID にしない。どちらも並び替えで動く。

## 合否の出し方

**スキルありの構成で、全採点項目の通過率が100%であることを合格とする。** 採点項目はすべて同じ重みで数える。
採点項目はどれも、スキルが明示的に指示していることか、依頼が明示した要件を確かめるものだけにする。
スキルを読んだうえで落ちる項目があるなら、スキルの書き方が足りないか、採点項目が誤っているかのどちらかなので、
重要度で区別せずに直す対象にする。スキルなし（または改善前のスキル）の通過率は、スキルの効き目を見る参考値である。

集計は skill-creator の `aggregate_benchmark.py` の pass_rate だけを使う。`grading.json` は skill-creator の標準の形だけにする。
条件に当たらない採点項目は、文言に書いた条件で「満たしたものとする」と決まるので、独自の「適用外」の欄は要らない。

そのため、採点項目には次を守らせる。

- **1行に1つの条件。** 2つの条件を持つ行は分ける。片方だけ満たした出力を判定できなくなる
- **主観で判定が割れる語で書かない。** 「適切」「分かりやすい」のような語ではなく、`SKILL.md` か `references/` の具体的な記述に結び付けて書く
- **条件に当たらないときの扱いを文言に書く。** 「〜のときは満たしたものとする」の形にする

## スクリプトで判定する採点項目

**構文を見れば誤りなく決まる採点項目は、採点役が目で見ずにスキル直下の `scripts/check.mjs` で判定する。**
skill-creator の SKILL.md も、プログラムで確かめられる項目はスクリプトで確かめるよう求めている。
採点項目が多いと、採点役が1項目を読み違える確率が小さくても、どこかで読み違える確率は大きくなる。
100% を合格とする基準では、その読み違いがそのまま不合格になる。機械的に決まる項目を採点役の判断から外し、
採点役には判断の要る項目だけを見させる。

**共通の採点項目を配るケースは減らさない。** 規約は、書くものによって読む references が違い（値オブジェクト・エンティティ・DTO・
インフラ・エラー class）、崩れ方も作業の種類ごとに違う。配る先を専用のケースに絞ると、ほかの作業で起きた崩れに evals が気づけなくなる。
採点項目の数とぶれは、スクリプトで判定する範囲を広げることと、依頼文と `files` から対象が現れえないことが確定するケースからだけ外すことで減らす。
どの規則のぶれが大きいかは、`RUNNING.md`「採点のぶれを測る」の手順で実測してから決める。

対象の採点項目は、文言の先頭（規則 ID の直後）に **〔スクリプト判定〕** を付けて区別する。
`evals.json` のキーは増やさない。採点役は `RUNNING.md` の手順でスクリプトを走らせ、結果をそのまま `grading.json` に写す。
スクリプトが `passed: null`（型が解決できないなど、スクリプトでは決められなかった）を返した項目だけ、採点役が文言どおりに判定する。

**規則の一部だけが構文で決まる採点項目は、印を付けず、スクリプトは確実な違反だけを返す。**
このときスクリプトの結果は `passed: false`（違反の箇所を `evidence` に示す）か `passed: null`（確実な違反は見つからなかった）のどちらかで、
`passed: true` は返さない。`false` はその箇所が採点項目の文言に反することが構文だけで言えるもので、採点役は箇所を確かめて fail にする。
`null` のときは、採点役が文言どおりに自分で判定する。規則 ID を「構文で決まる部分」と「判断の要る部分」に分けて行を増やす方法もあるが、
採点項目の数を増やさず、規則の ID と文言を変えずに済むので、こちらを選んだ（下の「証拠として使う判定」の表）。

判定するのは `--outputs` に渡した成果物のファイルだけである。渡した fixture のうち成果物に無いものは見ない。
TypeScript のファイルが1つも無い成果物（回答文だけの出力やレビュー）は、すべて passed になる。
`--files` を渡すと、判定するファイルをそのファイルだけに絞る（今回書いた・変えたファイルだけを判定し、既存のファイルの違反で
依頼の範囲の外を直させないため）。`vitest` の設定は絞らずに読む。`--help` で使い方を表示する。

各結果には、規則の1行の要約（`summary`）と、規則の本文がある見出し（`ref`。`references/<file>#<見出し>` か `SKILL.md#<見出し>`）を付ける。
`null` の項目や違反を直すときは、その見出しの規則を読む。見出しが実在することは `build.py` がいつも確かめる。

**スクリプトは、確かめきれないときに合格を返さない。** 次のときは `null` にする。
- 型の解決に頼る判定（`no-default`・`error-message-owned`・`error-fatal-shape`・`no-raw-error`・`error-message-form`・`local-name`・`dto-local-name`・`throw-concrete`・`test-name-error-class`・`gwt-adjacent`）は、
  `--tsconfig` を読めないとき、または判定するファイルの `import` を解決できないとき（出力の `typeUnreliable` に理由が出る）
- テストの呼び出しを見て決める判定は、テストのファイルなのに `test`・`it`・`describe` の呼び出しを1つも見つけられないとき

`test`・`it`・`describe`・`expect` は、`vitest` などから別名で import したもの（`import { test as check }`）や名前空間で import したもの
（`import * as v from "vitest"` の `v.test`）も元の名前として扱う。同じ名前をほかのモジュールから import しているときは、テストの API として扱わない。

| 規則 ID | スクリプトが見るもの |
|---|---|
| `no-cast` | 型アサーション。`as` 式と `<T>expr` の形（`as const` と `<const>` を除く）。テストファイルも対象。`import` の別名や文字列は構文上 `as` 式でないので数えない。非 null アサーション（`!`）は、規則の文（references/model-code.md「型アサーションを書かない」）が `as` を名指ししていて `!` に触れていないので数えない |
| `no-nested-ternary` | 三項演算子の中（関数の境界を越えない範囲）にある三項演算子 |
| `comment-period` | 行だけのコメントが続く範囲と、コードの後ろのコメントを1つのまとまりとし、その最後の行が「。」で終わるもの。`// Given:` などの見出しの行と `///` は除く。JSDoc とブロックコメントは見ない |
| `no-default` | 受け手の型が zod の型である `.default()`・`.prefault()`・`.catch()` の呼び出し。Promise の `.catch()` は数えない。受け手の型が解決できなければ `null` |
| `jsdoc-tags` | JSDoc の `@throws`・`@deprecated` 以外のタグと、1つの `@throws` に `Error` で終わる class 名が2つ以上あるもの |
| `no-guard` | 型の述語（`x is T`。`asserts` は除く） |
| `brand-symbol` | `.brand<T>()` の `T` が、同じファイルで `unique symbol` として宣言した名前の `typeof` でないもの。宣言の仕方だけを見る。`.brand()` が1つも無ければ適用外（`true`）。列挙・DTO・テストだけを書く作業では `.brand()` が無いのが正しく、書く側の手順（今回書いたファイルについて `false` を0件にする）を満たせなくなるため。ブランドを付けるべき完成値に付けているかは、採点役が判定する `[brand-present]` で見る |
| `brand-no-export` | `unique symbol` の宣言を export しているもの（`export { X }` を含む） |
| `brand-output` | `.brand<T, "inout">()` |
| `satisfies` | テスト以外のファイルで、`safeParse` にキーを持つオブジェクトリテラルを `satisfies` なしで渡しているもの。`satisfies` の型の名前が `SchemaInput` で終わらなければ `null` |
| `no-codec` | `z.codec(...)` と、`zod` からの `codec` の import |
| `no-in-source` | テスト以外のファイルの `import.meta.vitest` |
| `coverage-no-ignore` | テスト以外のファイルの `v8 ignore`・`c8 ignore`・`istanbul ignore` のコメント |
| `helper-not-imported` | テスト以外のファイルが `.helper.test` を import しているもの |
| `helper-no-test` | `*.helper.test.ts` の中の `test`・`it`・`describe` の呼び出し |
| `helper-exclude` | ヘルパーがあるとき、成果物の `vitest.config` を構文木で読み、`test.exclude` の配列に `helper.test` を含む文字列があるか。`coverage.exclude` と `typecheck.exclude` はテストの収集に効かないので数えない。コメントに書いた設定は読まない。`exclude` を変数やスプレッド・`mergeConfig` で組み立てていて値を決められなければ `null`。成果物に設定のファイルが無ければ `false` で、`evidence` に「作業場所に vitest の設定が無ければ新しく作れば消える。既存の設定を変えるときは利用者に確認する」ことを示す |
| `type-test-config` | 型のテスト（`*.test-d.ts`）があるとき、成果物の `vitest.config` を構文木で読み、`typecheck` の `enabled` が `true` の値か。`typecheck.include` を書いているときは、すべての `Xxx.test-d.ts` に当たる形（`**/*.test-d.ts`）なら `true`、それ以外は型のテストのファイルに当たるかを構文だけで決められないので `null`。コメントに書いた設定は読まない。値を変数などで組み立てていて決められなければ `null`。設定のファイルが無いときの `evidence` は `helper-exclude` と同じ |
| `type-test-file` | `*.test-d.ts` 以外のテストファイルにある `@ts-expect-error`・`expectTypeOf`・`assertType` |
| `type-test-single` | `*.test-d.ts` のテストと、`@ts-expect-error` を含むテストで、`@ts-expect-error` が1つでないもの、右に説明が無いもの |
| `test-not-it` | `it(...)` の呼び出し |
| `no-not-tothrow` | 引数なしの `.not.toThrow()`・`.not.toThrowError()` |
| `strict-equal` | `.toEqual(...)` |

**スクリプトにしなかったもの。** 次のどれかに当たる採点項目は、機械的に書けても採点役の判定に残した。

- 文言に判断の要る条件が付いている（`[safe-parse]` の「公開関数の戻り値型」）
- 対象を決めるのに意味の理解が要る（`[helper-file]` の「値オブジェクトとエンティティ」、`[public-api-section]` の「公開 API」セクションを置くべきファイル（モデルのファイルか）と既存の区切りの流儀、`[schema-outside]` の「完成値スキーマ」がどれか）
- 構文で決まる部分があっても、誤って数えるおそれがある（`[gwt-enum-pair]` の「定義済みの」は、列挙の値以外を指す文でも現れうる）
- 正規表現や API 名では漏れや誤りが出る（`[exact-optional]` は `.optional()` 以外の書き方でも任意項目になる、`[no-transform]` は内包する値オブジェクト経由の正規化も数える）
- 型検査とテストの実行（`[typecheck]`・`[tests-run]`）は、採点役がコマンドを走らせて判定しているので印を付けていない

**スクリプトの判定を足す・直すとき。** 1規則ずつ、次の4つをすべて満たすものだけを全面判定（印を付ける）にする。満たさないものは証拠として使う判定にするか、スクリプトにしない。
1. 採点項目の文言の条件がすべて構文で決まる
2. `example/` で違反が0件
3. 違反の例（`maintenance/checker-fixtures/<規則>/ng/`）で `false`
4. 決められない書き方（別名 import、変数で組み立てた設定、動的な文字列など）で `null`

確かめるのは `build.py --check-script --node-modules <dir>` で、期待する結果は `maintenance/checker-expectations.json` に書く。
**期待する結果は check.mjs の出力から写さず、規則の文（`evals.src.json`）と期待違反の一覧から決める。** 自己テストは次を確かめる。
- `example/` で `false` が0件
- `checker-fixtures/` の正しい例・違反の例・決められない例が、期待どおり `true`・`false`・`null` になる
- `fixtures/` の正しい見本は `false` が0件、違反を仕込んだ fixture は仕込んだ違反の規則だけが `false`
  （`warehouse/review-domain/` の V3・V4・V10・V13、`warehouse/reviewed-tests/` の V1・V2・V3・V5・V6・V9、`warehouse/infrastructure-under-review/` の I3・I4・I8・I9・I10・I11、
  `warehouse/legacy/` の `throw new Error`・`z.codec`・文字列のブランド。`shelf-app/` はケース19の既存の流儀なので `[test-file-place]` などが `false` になるのが正しい）
- `--help`・`--files`・`--tsconfig` が期待どおりに働く

判定を足すたびに、違反の例を1つ以上足す。
判定を変えたら、この表と採点項目の文言を揃える。文言と判定がずれると、採点役がスクリプトの結果を信じてよいか分からなくなる

## build.py

`evals.src.json` を読み、ケースごとに次の順で `evals.json` を組み立てる。

1. `inherits` の順にプロファイルの assertion を集める（まったく同じ文言は1つにまとめる）
2. `excludes` にある規則 ID を持つものを落とす
3. 残った共通の assertion の先頭に `[共通] ` を付け、ケース固有の assertion を後ろにつなぐ
4. 共通の assertion の差し込み（`{test_subjects}` はケースの `test_subjects`、`{violations}` はレビューケースの期待違反の一覧のパス）を置き換える
5. skill-creator の `evals.json` の形（`id`・`prompt`・`expected_output`・`files`・`expectations`）だけで出力する。`files` はスキルのルートからの相対パスにする。保守用のキーは出力しない

生成の前に整合を検査する。`files` の実在、レビューケースの V / I / D の行と `expected-violations/` の一覧、
`CASES.md` の除外の表と `excludes`、この文書のプロファイルの表と `inherits` である。

`--typecheck` を付けると、各ケースの `files` だけを一時ディレクトリに写して `tsc` も走らせる。
渡したファイルが渡していないファイルを import していると、受験者が何を書いても型検査が落ちるので、
fixture や `files` を変えたときは付けて確かめる。受験者に書かせるファイル（15番の `shared-errors.ts`）を
渡すファイルが import しているケースは、ケースの `typecheck_stubs` に「写し先 → 代役のファイル」を書き、
型検査のときだけ `fixtures/typecheck-stubs/` の代役を置く。代役は受験者には渡さない。

# 保守の手順

## 共通の流れ

どの変更でも最後は同じである。

1. `evals.src.json` を編集する（`evals.json` は触らない）
2. `python3 -B build.py` を実行し、エラーが無いことと件数の変化が意図どおりかを確かめる
3. `git diff evals.json` で、意図した行だけが変わったことを確かめる（コミット前に `build.py --check` でも確かめられる）
4. `CASES.md` を追随させる（「固有に測るもの」の列と除外の表。プロファイルの配布先はこの文書の表だけを直す）
5. fixture や期待違反を変えたら、`fixtures/README.md` と `expected-violations/` も追随させる
6. `evals.src.json` と `evals.json` を同じコミットに入れる

**assertion の文言を変えると、それ以前の `grading.json` とは文言で突き合わせられなくなる。**
比べるときは、規則 ID かケース番号と行の意味で対応付ける。
依頼文や assertion を変えたあとの run は、新しい iteration として扱う。

## ケース固有の assertion を足す・直す

1. **根拠が依頼文か fixture にあるかを確かめる。** 無い条件を要求するなら、先に依頼文を直す（下の「依頼文を直す」）。
   依頼文に書かないなら、境界を問わない文言にする
2. 下の「assertion の書き方」に沿って書く。とくに1行1条件、振る舞いで問う、判定の単位を書く
3. **同じ欠落を別の行が数えていないかを確かめる。**
   - 共通プロファイルの行と重なるなら、ケースの `excludes` に規則 ID を足し、`CASES.md` の除外の表に理由を書く
   - ケース固有の行どうしで、ある行の欠落を前提にする行があるなら、従属の条件を文言に書く（下の「適用条件と除外」）
4. **空虚に真にならないかを確かめる。** その機能を書かなかった出力でも通ってしまう行は、何も測っていない
5. テストに関わる行なら、`references/testing.md` と `testing-*.md` の必須グループとの対応（下の「テストの見方」の表）を直す

## 依頼文を直す

- **依頼文に書くのは業務の条件だけにする。** 桁あふれの境界、文字数の上限、金額の端数、並び順の基準など。
  `refine` を使う、`superRefine` にする、`z.templateLiteral` を避ける、といった実装の手段は書かない。
  書くと答えを渡すことになり、識別力が消える
- **罠の状況を消していないかを確かめる。** 8番は「退会しても記録を消さず、退会したことが分かるように残す」
  までを書き、退会の表し方（退会日時を持つか、状態で持つか）はあえて書いていない。ここに「退会日時を記録します」を足すと、
  「明示された操作を、表し方が決まらないことを理由に省かないか」を測る状況が無くなる。
  記録を残すか消すかは振る舞いが変わる選択で、指針が「その部分だけを質問する」例に挙げているので、依頼文で決めておく
- **依頼文どうしで条件が矛盾していないかを確かめる。** 割引率を完成値に持たないのに明細の追加で請求額を求め直させると、
  割引額をどう扱うかが依頼文から決まらない。11番は「明細を追加しても割引額は変えない」と書いて決めている
- **金額と率は、正しい実装どうしで結果が割れない形で渡す。** 割引率を小数で渡すと、`Math.floor(100 * 0.29)` が28になるように、
  浮動小数の誤差で1円ずれる。11番と25番は割引率をパーセント単位の整数で渡す
- 生成・誘惑・修正のケースの依頼文は「Zod を使ってください。」で終える。レビューのケース（21・22・26番）は付けない
- 参照実装の語彙を使わない

## 共通プロファイルの規則を足す・直す・改名する

1. **ID を決める。** 意味ベースで、既存の ID と重ならないもの。`SKILL.md` の規則番号を使わない
2. **どのプロファイルに置くかは、配りたいケースの `inherits` から逆算する。**
   上の「プロファイル」の表で、根拠にしたケースがそのプロファイルを継承しているかを確かめる
3. **配ったケースのうち、その規則が空虚に真になるケースを探し、`excludes` に足す。**
   対象の無い assertion を配ると、採点役がその場の裁量で適用外にし、分母がケースごとに揺れる
4. **改名するときは、次をすべて直す。** `build.py` が検出するのは3つ目だけである
   - プロファイルの行
   - `expected-violations/*.md` の規則 ID の列（プロファイルにある ID は規則辞書を兼ねている）
   - 各ケースの `excludes`
   - `CASES.md` の除外の表
5. 意味を変えたのに ID を変えないと、過去の結果と比べたときに別物を同じ ID で比べることになる。
   意味が変わるなら ID も変える

## ケースを足す

1. **何を測るかを1つに決める。** 既存のケースで測れていないことか、`CASES.md` で確かめる
2. **種別と、基準か識別かを決める。** 識別ケースなら、参照実装をそのまま使うと落ちる業務条件を1つだけ入れる
3. `name` を決める。接頭辞を付け、**`key` を含めない**
4. 題材を図書館（生成）か倉庫（レビュー・修正）から採る。参照実装の語彙を使わない
5. `inherits` を上の表から選び、空虚に真になる ID を `excludes` に足す
6. `files` が要るなら fixture を用意する（下の「fixture を足す・直す」）
7. 依頼文、`expected_output`、ケース固有の assertion を書く
8. `id` を通し番号で振り、`CASES.md` に行を足す
9. `build.py` を実行する
10. 基準ケースか識別ケースかを、`CASES.md` の表と `discriminative` の両方に書く

## fixture を足す・直す

- **型検査が通る状態にする。** 違反を仕込んだ fixture も型検査は通す。レビューが型エラーの指摘に流れないようにするため
- **仕込んだ壊れ方を実行して確かめる。** 期待違反に「往復が壊れる」と書くなら、実際に壊れることを確かめる
- **生成・修正のケースの fixture にテストを置かない。** テストを添えると、「どこまで確かめるテストを書けるか」の答えを渡すことになる。
  置くのは、既存の流儀に合わせることを測る19番と、テストそのものをレビューさせる26番だけである。
  26番の fixture は生成ケースの題材と混ざらないよう倉庫にする。
  修正後の正解・期待違反・採点用の誤実装は fixture に置かず、採点側だけが持つ
- **ディレクトリ名・ファイル名に `key` を含めない**
- ケースの `files` に並べ、`fixtures/README.md` の表を直す
- 期待違反は `fixtures/` に置かず、`expected-violations/` に置く

## レビューの期待違反を直す

- fixture に仕込んだ違反と `expected-violations/<ケース名>.md` の一覧を、同じ変更で直す
- 一覧の番号（`V1` `I1` `D1`）と、ケース固有の assertion の接頭辞を一致させる
- **違反1件につき assertion を1行、おとり1箇所につき1行置く**（下の「レビューケースの採点」）
- 判定が割れた指摘の数え方は、一覧の「判定で気をつけること」に足す。採点役はここを読む

## SKILL.md や example/ を変えたとき

1. **規則を逆転・廃止・改名したら、その規則を問う assertion を探して直す。**
   プロファイル、ケース固有の行、`expected-violations/` の是正の向き（「逆向きの主張の例」を含む）を検索する。
   怠ると、禁じた書き方を「満たすべき」とする行が残る
2. **規則を足したら、それを測る行が要るかを決める。** 要るなら、配るプロファイルか、発火する依頼文のケースを選ぶ
3. **参照実装を変えたら、基準ケースが写して通る前提が崩れていないかを確かめる。**
   参照実装のコメントを変えたなら、`[no-echo-comment]` と `[comment-accurate]` の判定に影響しないかも見る
4. fixture が現行の規則どおりであることを確かめ直す。「正しい見本」の fixture が規則に遅れると、
   基準ケースの通過率が原理的に100%にならず、レビューケースでは正しい指摘が偽陽性に数えられる
   （`fixtures/README.md`「意図的に残した逸脱」に無い逸脱は直す）

## 読ませ方の保守

**`SKILL.md` の「読む計画」の表が、書くものごとに読むファイルの正である。** 各 references の冒頭の表はその写しで、
セルにはファイル名だけを書く（節は指さない。例外は、見出しで引く辞書の `pitfalls.md` と、`patterns.md` が `describe` の名前で範囲を指す `example/domain/entity/Task.test.ts` だけ）。

`maintenance/rule-map.json` は次を持つ。

| キー | 中身 |
|---|---|
| `rules` | 採点項目の規則 ID → その規則の本文がある `SKILL.md`・references のファイル（どれか1つに届けばよい） |
| `moved` / `moved_files` | 読ませ方の整理で移した節とファイル |
| `changed_lines` | 移動と読み方の整理のために文言を変えた行（読み方の表、相互参照、位置語、〔check.mjs〕の印、「SKILL.md の表が正」の1行）。これ以外で規則の文は変えていない |

`build.py` は、各ケースの `reading_rows` で選んだ行のファイル（と `SKILL.md`）から、そのケースに配る規則の本文のファイルに届くことを確かめる。
届かないと止まるので、行を足すか、規則の本文の置き場を見直す。**規則を足したり、references の見出しやファイルを変えたりしたら、`rules` と `reading_rows` も直す。**

**読む量の記録。** 代表の4作業について、読む計画どおりに読んだときの必読（`SKILL.md` と references）と、`patterns.md` が名指しした example の合計を UTF-8 のバイト数で測った。
変更前は読ませ方を整理する前（`model-code.md` を節で読み、`errors.ts` のテストの節を `test-style.md` に含めていた版）である。
`pitfalls.md` は横断検証の2つの見出しだけを数え、ほかの API の見出しは作業によって違うので数えない。

# assertion の書き方

誤判定を生む書き方と、その直し方をまとめる。

**1つの assertion に2つの条件を入れない。** 「`z.string()` で受けてから pipe している
（`templateLiteral` を先頭に置いていない）」は、pipe の使用と `templateLiteral` の位置という
独立した2条件が1文に入っていた。`templateLiteral` を使わない実装は括弧内の懸念が
起きていないのに、本文で落ちた。条件ごとに行を分ける。
「978 と 979 の ISBN を生成・復元できることをテストで確かめている」のように4通りの組み合わせを1行に入れると、
1本欠けただけで行全体が落ちる。

**実装の形ではなく、振る舞いで問う。** 「`z.url()` の手前に空白を拒否する `refine` がある」は、
`z.url()` を使わない実装に何を見ればよいか決まらず、その実装が末尾の空白を受理する穴を持っていても検出できない。
「前後に空白を付けた URL が拒否される」と書けば、実装形に依らず測れる。

**有無で通る文言にしない。** 「桁あふれのエラー class がある」は、使われていない class を
置いただけで通る。「合計が `Number.MAX_SAFE_INTEGER` を超える入力で、その class のエラーが投げられる」と
書く。「識別子で等価性を判定している」も、等価性の関数を持たずに ID を比べているだけの出力が通ってしまう。
**その機能を書かなかった出力で試しに読んでみて、通ってしまうなら書き直す。**

**観測の手段を、別の欠落に縛らない。** 「余剰キーを足した値を型ガードに渡すと false になる」は、
型ガードの無い出力で何を見ればよいか決まらず、採点役の裁量が入った。
「完成値スキーマで検証すると失敗する」にする（型ガードは規約で書かせない。規則14）。

**「決めている」「触れている」で終わらせない。** 何をもって決めたと見なすかが
採点役ごとに変わる。「JSDoc かテストのいずれかで明示されている」まで書く。
回答文で説明させたいなら、何の説明が要るのかを書く
（「形式の検証をどこが担い、本人確認をどこが担うかを説明している」）。

**依頼文に無い条件を assertion で要求しない。** 依頼文に桁あふれの条件が無いのに
`Number.MAX_SAFE_INTEGER` を名指しする assertion を置くと、
同じケースに掛かる「依頼に無い不変条件を足さない」と正面から衝突する。
測りたいなら依頼文に書く。書かないなら、境界を問わない文言にする。

**依頼された機能そのものを見る assertion を置く。** 規則の遵守ばかり並べると、
依頼の中身を満たしていない出力が全通過しうる。列挙のケースで区分をいくつ書いたかを見る行が無ければ、
区分が足りなくても満点が取れる。依頼された操作を直接見る行が無ければ、操作が無い出力の欠落は間接的な行に散る。

**創作の広さを1行に押し込めない。** `[no-invention]` の1行だけでは、依頼に無い操作を1つ公開した出力と
5つ公開した出力が同じ1件の fail になる。公開面の広さは `[no-extra-api]`、
保存する項目・状態・数値は `[no-invention]` と、担当を分けている。

**レビューのおとりは、指摘の方向を問わない文言にする。** 「保存キーの regex を写しとして指摘していない」は、
同じ regex を「緩すぎる」と逆方向から指摘した出力を通してしまう。「regex そのものを問題として指摘していない」と書く。

# 適用条件と除外

## 空虚に真になる行を配らない

プロファイルの継承だけでは、対象によって空虚に真になる assertion が混ざる。
依存を持たない値オブジェクトに「共有の依存ファイルを作っていない」を掛けても意味がない。
次のような除外を持たせる。

- 列挙にブランドを求めない
- DTO に `create` / `reconstruct` を求めない
- 注入した依存が投げるものしか伝わらない関数に、`@throws` を求めない（依存が投げるものは、そのインターフェースの `@throws` が担う）
- `Result` を使うプロジェクトのケースに、既定の `DomainError` 階層を強制しない

`inherits` で配った assertion のうち、そのケースで空虚に真になるものは
`excludes` に規則 ID を並べて落とす。

**適用対象の無い assertion をケースに配らない。** 継承だけで配ると、
題材に対象が存在しない assertion が混ざり、採点役が毎回その場の裁量で
適用外にすることになる。除外の根拠がどこにも残らず、分母がケースごとに揺れて
比較できなくなる。プロファイルを細かく割って `inherits` で選ぶ。
単一プリミティブの値オブジェクトに入れ子の凍結を問う、といった空振りを避ける。

## 適用条件は課題と fixture から決める

**生成物から決めない。** 「生成物に操作が無いから操作の規則は適用外」と自動判定すると、
必要な操作を省略した出力が合格してしまう。「全状態で分岐する箇所がある場合」のような、
生成物に依存する条件を行に付けない。

## 欠落を二重に数えない

生成関数が無い出力に対して、名前を問う assertion と export を問う assertion の両方が落ちると、
通過率が実力より低く出る。片方に条件を書いて、1回だけ数える。

**「適用対象を決める条件」と「従属する観測の条件」を分ける。** 前者は課題と fixture から決まる
（上の節）。後者は、ある欠落を数える行が別にあるときに、その欠落を前提にする行を落とすための条件で、
**文言に元の行を名指しして書く。**

```
[impl-factory-export] 生成関数を名前付きで export している（生成関数が無いときは満たしたものとする。欠落は [impl-factory-name] で1回だけ数える）
```

名指しの無い条件で、生成物から適用外を決めない。

**同じ設計判断を2つの行で数えない。** 「正規化しない」を `[no-transform]` とケース固有の行の両方で数えると、
1つの逸脱で2行が落ちる。1・2番は `no-transform` を `excludes` に入れ、ケース固有の行で1回だけ数えている。
ケース固有の行どうしも同じで、1番の `toLowerCase` と `trim` は「値を変える段を繋がない」の1行にまとめている。class で実装した出力が、生成関数が無いという1つの選択で `impl-*` の複数の行を
連鎖して落とすのも同じである。

# テストの見方

スキルはテストの**観点**（`references/testing.md`）と**書き方**（`references/test-style.md`）の両方を定めている。
eval もこの2つを分けて測る。観点は下の表のとおりケースの固有観測に配り、書き方は `test-style` プロファイルで配る。

**「テストファイルがある」は存在確認にすぎない。**
そのテストが誤実装を落とせるかを見る。`references/testing.md` と `testing-*.md` の必須グループを、
それを測れるケースの固有観測に1つずつ配る。

| 必須グループ | 配った先 |
|---|---|
| 副作用（生成器を呼ばない） | 11（呼び出しを記録する依存。個々の入力の不正と、入力だけで決まる導出の失敗を別の行で見る） |
| 型の否定テスト（`@ts-expect-error`） | 8（ブランド付きの項目に生の値。依頼の識別子が1種類なので別種の識別子は測らない。余剰キーの型のテストは書き方の規則で求めない） |
| 独立に書いた期待対応 | 12（変換関数から作らない） |
| 横断検証が例外を投げない | 10（重複・要素不正・配列でない入力） |
| エラーの種別 | 5（具象の class を `toThrow` か、捕まえて `toBeInstanceOf` で確かめる。`not.toThrow(別の種別)` は何も投げない誤実装を通すので求めない） |
| エラー class の実行時の契約 | 15（生成と復元の失敗の種別の独立を `not.toBeInstanceOf`、`issues` の件数と `path`、`cause`、`name`、`FatalUnreachableError` の直接生成） |
| 導出値と副作用 | 25（再計算、再計算を忘れた保存値の拒否、生成器を呼ばないこと、完成値スキーマの検証が例外を投げないこと） |

**書き方を配るのは、既存のテストの流儀を持たないケースだけである。**
スキルは、既存の流儀と `test-style.md` の既定がぶつかる項目だけを利用者に確認させ、利用者の明示の指示には
確認せず従わせる。確認できない場面（eval のような非対話の実行）では既存の流儀を優先し、そう判断したことを
回答に書かせる。19番（既存のテストの流儀がある）は既存の流儀で書くことを固有観測で見るので `test-style` を配らず、
`test-core` だけを配る。18番（観点を `Result` に読み替える）は既存コードにテストの流儀が無いので、
`test-core` と `test-style` の両方を配り、読み替えたことを固有観測で見る。

**範囲外のテストを求めない。** スキルのテストの範囲は本物の外部接続を使わずに手元で完結するもので、
リポジトリ実装とドメインサービス実装はクライアントをモックに差し替えて確かめる。本物のクライアントで
実際の保存先に接続するテストだけを求めない。13・14番は、モックに差し替えたテストで確かめるべき観測を固有の行に置く。

**テストの有無と検出力は別の assertion にする。** 1つにまとめると、テストを1本も
書かなかった出力が「有無」の時点で落ちて、検出力を測る前に終わり、スキルの有無の差が出にくくなる。

**採点のときにテストを実際に走らせる。** 生成物だけからは「テストが通る」という
主張を確かめられない。回答文が書いた件数と実際の件数が違うこともある。採点役に `vitest` と `tsc` を実行させ、
結果を共通の採点項目 `[typecheck]` と `[tests-run]` の evidence に書かせる。

テストの行で、判定が割れうる点:
- 製品コードを通らないテスト（テストファイル内で定義した関数を検査している）は、`[test-power]` で落とせない形に数える
- 「期待値を変換関数から作らない」は、出力全体をリテラルと比べることか、変換の出力を期待値に使う箇所が無いことか、2通りに読める。`test-style.md` は DTO の保存表現をヘルパーにせず各テストに書き下ろすと定めているので、`[helper-reconstruct]` の観測と合わせて判定する
- `[ts-expect-error-scope]` で、実行時の検査に不正な値を渡すために置き、型の拒否も兼ねている抑止をどう扱うかは決めていない
- `[test-exists]` をファイル単位で見るか振る舞い単位で見るかは決めていない。本物のクライアントを使うテストを範囲外とすることと、エラー定義の扱いだけを文言に書いている
- `as` を使わずに偽のクライアントを書くには、型引数を付けない `vi.fn()` を使う。ジェネリックな `send` の型に `as` 無しで代入できる（`vi.fn<DynamoDBClient["send"]>()` は TS2322 になる）。`references/test-style-mocks.md` の「クライアントのモック」に書いてある

# レビューケースの採点

- **`expected-violations/` に出てくる規則 ID のうち、プロファイルに無いものは、一覧の中だけで使う ID である。**
  `no-throw-in-check` や `key-integrity` のように、レビューの対象を指すだけで
  生成側の assertion には現れない ID がある。プロファイルが規則辞書を兼ねているので、
  プロファイルにある ID は改名したら両方を直す
- 期待違反は `expected-violations/<ケース名>.md` に持つ。`fixtures/` の中には置かない。
  **モデルには渡さない。** 実行役に渡すのは `files` に並べたファイルだけである
- **検出は違反ごとの観測で測る。** 「期待違反をすべて挙げている」という1つの
  assertion にまとめると、11件のうち10件を挙げた出力と1件も挙げない出力が同じ fail になる。
  ケース固有の観測を違反1件につき1行置き、おとりを挙げていないことも1行ずつ置く
- 検出の単位は「fixture 内の特定の違反」。規則 ID を列挙しただけでは検出にしない。
  場所・問題の内容・根拠を対応付ける
- **1つの指摘が複数の箇所に触れていたら、箇所ごとに分けて数える。** 誤った主張が併記されていることを
  理由に、別の箇所の正しい検出を消さない
- **直し方が複数書かれていたら、最終的に推奨している案で判定する。** 書かれた順番で判定しない
- **一覧に無い誤った指摘は `[no-false-positive]` の1項目で見る。** 「違反に見えるが正しい箇所」は
  おとりとして D の項目で別に持つ。おとりだけで見ると、無関係な指摘を大量に足しても落ちない
- **逆向きの主張は検出に数えない。** 箇所は合っていても、現行の規則と逆の方向に直せと述べていれば、
  その V / I の項目を passed にしない
- 同じ箇所に複数の規則が付く違反には、許容する根拠 ID を副 ID として持たせる
- 規則辞書をモデルに渡さないなら、ID の完全一致を要求しない。
  採点側が指摘を ID へ対応付ける

# 「質問で止まる」出力の扱い

SKILL.md の「依頼に書かれていないことの扱い」に対応させている。

- **`trap-underspecified`（20番）は、コードを書かず質問だけを返すことが正解である。**
  項目も操作も手掛かりが無く、モデルを定義できない依頼だからである。共通プロファイルを外し、
  固有観測だけで判定する。**コードを書いた出力は、説明を添えていても「コードを書いていない」の行で落とす**
  （「書いた場合は説明していればよい」という合格経路を置くと、最小実装を出す出力が通る）
- **それ以外のケースでは、質問だけで実装しない出力を合格にしない。**
  依頼文に仕様が書いてあるなら、決まらない部分だけを質問し、決まっている部分は実装まで出す
- 8番は、記録を残すことまでを依頼文で決め、退会の表し方が決まらない状況をあえて残している。
  表し方を理由に退会を省いた出力は、依頼された操作を見る行で落ちる
- 1番は「大文字小文字は同一視して扱いたい」と明示された依頼なので、同一視の要件を捨てる実装は
  依頼未達である。ドメインで正規化しないことと、同一視の要件を無視することは別である。
  等価性の関数で大文字小文字を区別せずに比べる、アダプタ層の正規化として述べる、受理する表記を確認する、のどれも合格にする

**実行役への共通の手順に、質問で止まるべき状況を書かない。** 書くと、20番で測りたいスキルの判断を
手順が肩代わりする。手順に書くのは「成果物が回答文だけの場合もある」までにとどめる。
「型検査とテストを走らせて通ることを確かめる」とだけ書くと、コードを書くことを促してしまう。

# 判定でやってはいけないこと

採点役の手順（`RUNNING.md`）にも同じ内容を書いている。assertion を書くときも、
この判定を採点役に求めることにならないかを確かめる。

- **`as` 禁止を文字列検索で判定しない。** `as const`、`import` の別名、
  レビューで引用した違反例を誤検出する。構文として見る
- **API 名の一致で落とさない。** 横断条件が1つなら `refine` で足りる。
  `superRefine` を必須にすると、参照実装と同じ書き方の正解を偽陰性にする。
  見るのは「横断条件の issue に `path` が付いている」ほうである
- **「regex が区切りだけ」を要求しない。** 保存キーは接頭辞・区切り・連番の
  固定幅を検証してよい。禁じているのは業務上の文字種と長さの転記である
- **定数の `import` を一律に禁じない。** 禁じているのは DTO へのドメイン定数の
  持ち込みである。採番実装がドメインの番号上限を `import` するのは正しい
- **`FatalUnreachableError` をファイル単位で禁じない。** 外部応答の検証に使うのは誤り、
  検証済みの部品から組み立てた値の検査に使うのは正しい。判定単位は失敗の分岐である
- **指針に同じ記述があることを理由に、コメントを言い直しと判定しない。**
  その場所に効く挙動や壊れる仕組みを説明していれば `[no-echo-comment]` は pass。
  コメントが実装と食い違っているかは `[comment-accurate]` で別に見る
- **生成物を見て適用外を決めない。** 適用外にしてよいのは、文言が適用外の条件を書いているときと、
  従属する観測で元の欠落を別の行が数えているときだけである

# 運用の注意

- **ケース名・ディレクトリ名に `key` を入れない。** 権限設定の read deny パターン `**/*key*` が
  効いて、採点役がそのディレクトリを読み書きできなくなる
- **19番の `biome.json` は `"root": false` である。** このリポジトリの formatter が fixture の
  流儀を書き換えないためで、採点役が整形を検証するときは fixture ごと複製して
  複製側を `true` に書き換える。`--config-path` は `root: false` の設定を拒否する。**実行役に渡す複製も `true` にし、実行役の `node_modules` に biome を入れる**（`RUNNING.md`）。そうしないと、スキルの手順どおり整形した実行役の出力が既定の書式に書き換わり、この項目で落ちる
- **`eval_metadata.json` は実行中はケースのディレクトリに置かない。** 実行役が assertion を
  見てしまう。実行が終わってから書く（`RUNNING.md` の手順どおり）
- **`expected_output` も実行役に渡さない。** ケースの意図がそのまま書いてある
- **スキルと eval の語を揃える。** SKILL.md が「依頼された操作の実装に不可欠な項目」と書くなら、
  `[no-invention]` の適用除外も同じ語で書く。語がずれると、採点役が別の基準で読む
